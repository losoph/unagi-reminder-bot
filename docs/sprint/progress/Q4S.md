## Q4S Упрощение проекта Очереди 4 до модели «папка = одна рассылка»
- Решение: Переработать проектную архитектуру Очереди 4 (`docs/sprint/queue4-design.md`) под окончательную плоскую модель «папка = одна рассылка» (решения владельца и аудит Argon от 18.10.2026, `docs/sprint/argon-owner-model-2026-10-18.md`): папка дайджеста = одна рассылка с ОДНИМ расписанием (только день, или только неделя, или только месяц) и одним временем доставки (у ежедневной папки — опциональные доп. слоты в настройках, один курсор); системная папка «Основной» (`is_default = 1`) для подписок без папки (`tag IS NULL`, не удаляется, пустая скрыта в UI); канал состоит ровно в одной папке; курсор — строго один на подписку (`subscriptions.last_post_id`), таблица курсоров на пару расписание-подписка полностью исключена; FSM-мастер новой папки (период → время → доставка) с атомарным созданием папки и подписки в конце; перенос канала или смена периода папки сопровождается подрезкой курсора окном нового периода (`now - new_period`) и пересчётом `next_send_at`; удаление папки с выбором `[Перенести в Основной]` / `[Отписаться]`; почтовые подписки мигрируют в папки с `delivery = 'email'` (без UI-шага), планировщик вызывает текущий `email_digest` (TG1), позже — контракт JSON v1 для `ghsub` в файловый спул без ворот G3; нарезка T20…T23 пересчитана под новую модель.
- Диагностика и dry-run: `ops/migrate_schedules_dryrun.py` адаптирован под модель «папка = одна рассылка»: убран расчёт курсоров на пару; добавлена проверка однородности `period` внутри каждой папки (включая папку «Основное» при `tag IS NULL` и проверку на `NULL`) с выдачей конфликта (код возврата 3); учтена миграция email-подписок в расписания с `delivery = 'email'`; набор тестов `tests/test_migrate_schedules_dryrun.py` расширен до 18 тестов с проверкой неоднородности в именованных папках и в папке «Основное», однородных папок и валидности неизменности БД.
- Компромисс: Миграция строгая — любые неоднородности периодов внутри папок, дублирование каналов или расхождения времени приводят к коду возврата 3 и требуют ручной корректировки владельцем в БД до запуска мигратора T20.
- Для следующей очереди: Провести запуск dry-run на актуальном снимке прод-БД (T19). При коде 0 приступить к реализации схемы и строгой миграции T20.
