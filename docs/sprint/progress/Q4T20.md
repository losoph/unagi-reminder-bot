# Журнал решений: T20 — Схема папок/выпусков и строгая миграция (Очередь 4)

- **Задача**: T20 (Очередь 4, модель «папка = одна рассылка»).
- **Ветка**: `feat/q4-t20-schema`.
- **Маркер коммита**: `(Q4T20)`.

---

## 1. Архитектурные решения и изменения схемы

### 1.1. Новые таблицы (§3.1)
В `data/database.py:init_db()` добавлены DDL для целевой модели данных:
1. `folders`: сущность папки-рассылки с расписанием. Ограничения:
   - `UNIQUE(user_id, name)` — защита от дублирования папок у пользователя;
   - `CHECK (period IN ('daily', 'weekly', 'monthly'))`;
   - `CHECK (send_hour BETWEEN 0 AND 23)`;
   - `CHECK (send_minute BETWEEN 0 AND 59)`;
   - `CHECK (monthly_mode IN ('date', 'weekday', 'last_day'))`;
   - `CHECK (delivery IN ('telegram', 'email'))`;
   - Индексы: частичный `idx_folders_due` (`WHERE next_send_at IS NOT NULL`) и `idx_folders_user`.
2. `digest_editions`: снапшот выпуска дайджеста до отправки для гарантии идемпотентности:
   - Внешний ключ `folder_id REFERENCES folders(id) ON DELETE CASCADE`;
   - Уникальность `UNIQUE(folder_id, scheduled_at)`;
   - Индексы: `idx_digest_editions_user_status`, `idx_digest_editions_sched_status`.
3. `digest_edition_items`: зафиксированные публикации выпуска:
   - Внешние ключи на `digest_editions(id) ON DELETE CASCADE` и `subscriptions(id) ON DELETE CASCADE`;
   - Уникальность `UNIQUE(edition_id, channel_username, post_id)`;
   - Поле `post_text` сохраняет текст поста для безопасного повтора даже после 30-дневного cleanup `channel_posts`;
   - Индексы: `idx_edition_items_edition`, `idx_edition_items_sub`.

### 1.2. Модификация существующих таблиц (§3.2)
Колонки и индексы добавлены через стандартный для `init_db()` паттерн с перехватом `OperationalError`:
1. `subscriptions.folder_id INTEGER REFERENCES folders(id) ON DELETE RESTRICT` и индекс `idx_subscriptions_folder(folder_id, is_disabled)`.
2. `user_prefs.digest_scheduler_version TEXT DEFAULT 'v1'`: гарантирует, что существующие и новые пользователи остаются на legacy-планировщике v1 до персонального cutover в T21.
3. `digest_executions.folder_id INTEGER REFERENCES folders(id)` и частичный уникальный индекс `uq_digest_executions_folder_slot ON digest_executions(folder_id, scheduled_at) WHERE folder_id IS NOT NULL`.
4. `digest_alerts.folder_id INTEGER REFERENCES folders(id)` и частичный уникальный индекс `uq_digest_alerts_folder_slot ON digest_alerts(folder_id, scheduled_at, alert_type) WHERE folder_id IS NOT NULL`.

## 2. Выбор и компромиссы

### 2.1. Режим PRAGMA foreign_keys
- **Решение**: `PRAGMA foreign_keys = ON` **НЕ включен глобально** в `data/database.py:get_connection()`.
- **Обоснование**: В текущей кодовой базе SQLite foreign keys не включены ни в одном обработчике. Глобальное включение `PRAGMA foreign_keys = ON` на этапе T20 может непредсказуемо изменить поведение работающего планировщика v1, хэндлеров удаления подписок или тестов, создающих частичные фикстуры.
- **Где FK включены**:
  1. В соединении мигратора `ops/migrate_schedules.py` (перед открытием транзакции `BEGIN IMMEDIATE`);
  2. В специализированных тестах схемы `tests/test_q4_t20_schema.py` для верификации `CASCADE` и `RESTRICT`.

### 2.2. Расхождение по почте и флаг `--email-folders` (Открытый вопрос владельцу)
- **Расхождение**:
  - В проектном документе `docs/sprint/queue4-design.md` (§4.1 п.4) указано: если у пользователя есть подтверждённый email и период входит в `email_periods`, папка получает `delivery = 'email'`.
  - В решении владельца от 18.10.2026 (`docs/sprint/owner-decisions-2026-10-17.md`, разд. «Ответы владельца», п. 3 и подраздел «Пересмотр после аудита Argon»): *«Почта уходит в ghsub... для папок доставку по почте сейчас не назначаем, если это лишние шаги и код, не переживущие переход. Существующие email-подписки пока на старом пути (period) без миграции»*.
- **Решение**:
  - По умолчанию мигратор `ops/migrate_schedules.py` создаёт **все папки с `delivery = 'telegram'`**, не считывая `user_emails`/`email_periods` для записи расписаний. Существующие email-пользователи продолжают получать рассылку по legacy-пути v1.
  - Для явного перевода email-пользователей в `delivery = 'email'` предусмотрен флаг `--email-folders`.
- **Вопрос владельцу**: Требуется ли переводить 2 текущих email-пользователя в папки с `delivery = 'email'` на этапе T21, либо оставить их на legacy-пути до подключения спула JSON v1 к сервису `ghsub`?

### 2.3. Строгая миграция без авторазрешения конфликтов
- В соответствии с решением владельца от 18.10.2026 автоматическое разрешение конфликтов полностью исключено:
  - Никакого автоматического слияния папок;
  - Никакого выбора «старшего периода» (`monthly > weekly > daily`);
  - Никакого автоматического отключения конфликтующих подписок.
- При обнаружении любых конфликтов (`has_conflicts = True`) скрипт завершается с кодом возврата **3**, и база данных **не изменяется** (файл даже не открывается на запись, что подтверждено проверкой SHA-256 хеша в тестах).

### 2.4. Сохранение курсоров и v1
- `subscriptions.last_post_id` при миграции не модифицируется: текущие курсоры каналов остаются нетронутыми.
- `user_prefs.digest_scheduler_version` остаётся `'v1'` (или выставляется `'v1'` при отсутствии). Планировщик v1 продолжает бесперебойную работу.

## 3. Порядок запуска владельцем на проде (Runbook)

> [!IMPORTANT]
> Данный раздел является инструкцией для владельца. Агент не запускает команды на продакшене.

1. **Создание резервной копии базы данных (T19)**:
   ```bash
   python3 ops/aiqu/backup_db.py --tag pre-q4s
   ```
   Убедиться, что снимок создан и `PRAGMA quick_check` вернул `ok`.

2. **Проверка конфликтов данных на копии БД (Ворота G1)**:
   ```bash
   python3 ops/migrate_schedules_dryrun.py /path/to/backup_copy.db
   ```
   - Если код возврата **0**: база чиста, переход к шагу 3.
   - Если код возврата **3**: миграция заблокирована. Владелец устраняет конфликты в БД вручную, после чего повторяет проверку.

3. **Остановка контейнера бота**:
   ```bash
   docker compose stop unagi-bot
   ```

4. **Выполнение миграции с фиксацией в БД**:
   ```bash
   # Стандартный режим (email остаётся на legacy-пути v1):
   python3 ops/migrate_schedules.py storage/bot_data.db --apply

   # Либо, если принято решение перевести email в папки:
   # python3 ops/migrate_schedules.py storage/bot_data.db --apply --email-folders
   ```
   Убедиться, что код возврата **0** и выведено сообщение `[УСПЕХ] Миграция успешно завершена`.

5. **Запуск контейнера бота**:
   ```bash
   docker compose start unagi-bot
   ```
   Проверить логи контейнера на отсутствие ошибок:
   ```bash
   docker compose logs -f --tail=100 unagi-bot
   ```

6. **Процедура отката (при необходимости)**:
   При возникновении непредвиденных сбоев:
   ```bash
   docker compose stop unagi-bot
   python3 ops/aiqu/restore_db.py --tag pre-q4s
   docker compose start unagi-bot
   ```
   *Замечание: прямое копирование `cp` поверх живой WAL-БД запрещено во избежание повреждения SQLite.*
