# T20-split — режим разрешения конфликтов G1 «разбить папку по периодам» (ветка feat/q4-t20-schema)

Контекст: dry-run G1 на копии прод-БД (малая прод-база) дал код 3. Реальные конфликты: (а) 6 папок с подписками разных period (Основное: daily+weekly+monthly, Partners/Digital/TG: daily+weekly, News: daily+weekly); (б) один канал подписан дважды (теги Digital и Partners, периоды daily и weekly); (в) «расхождение next_send_at» в папке — в v1 это поле на подписку, различие ожидаемо и конфликтом быть не должно. Владелец разрешил авторазрешение конфликтов на 3 часа; Jev (1.0) за разбиение по периодам. По умолчанию строгое поведение остаётся: без нового флага код 3 и запись не делается.

ЧТО СДЕЛАТЬ
1. Новый флаг `--split-by-period` в ops/migrate_schedules.py (и в analyze_migration через параметр, чтобы dry-run тоже показывал результат с этим режимом):
   - Тег-группа активных подписок с несколькими period разбивается на папки по period. Самый частый period (при равенстве — более короткий: daily < weekly < monthly) сохраняет имя тега (для безтеговой группы — системную папку «Основное», is_default=1, period daily если он есть, иначе самый частый); остальные получают имя «<тег> — неделя» / «<тег> — месяц» / «<тег> — день» (для безтеговой «Основное — неделя»…), is_default=0. Имена проверять на casefold-коллизию с существующими тегами пользователя; коллизия — конфликт, код 3.
   - Каждая подписка сохраняет свой period и свой last_post_id: поведение доставки не меняется.
   - Папка получает время из digest_settings по её period (как сейчас).
2. Конфликты, которые режим снимает: heterogeneous_period_in_folder (после разбиения), channel_in_multiple_periods в разных папках — вместо конфликта предупреждение «канал в нескольких папках — решить до cutover v2 (T21)». Конфликт channel_in_multiple_tags при разных period превращается в то же предупреждение; тот же канал дважды В ОДНОЙ папке с одним period остаётся конфликтом (код 3).
3. «Расхождение next_send_at в папке» (time_discrepancy_in_folder) больше не конфликт ни в одном режиме, а информация в отчёте (next_send_at папки пересчитает T21). Это правка и в ops/migrate_schedules_dryrun.py; обнови его тесты, не ослабляя остальные проверки.
4. Остальные конфликты (неподтверждённая почта, некорректные параметры, casefold-коллизии, пустые теги) остаются строгими и дают код 3.
5. Таблица «ЦЕЛЕВЫЕ ПАПКИ» в отчёте показывает итоговые папки после разбиения; отдельный блок «РАЗБИТЫЕ ПАПКИ» (было → стало) и блок «ПРЕДУПРЕЖДЕНИЯ ДО CUTOVER».
6. Тесты на tmp-БД: смоделируй прод-случаи (Основное daily+weekly+monthly, Partners daily+weekly, канал дважды в Digital/Partners, News с paused-подпиской): без флага код 3 и БД неизменна по хэшу; с флагом --apply: число папок и привязок верно, last_post_id и period подписок не изменились, повторный запуск ничего не меняет, инвариант folder_id IS NULL = 0; дубль в одной папке остаётся конфликтом.
7. docs/sprint/progress/Q4T20.md: решение, обоснование (Jev, данные G1), и что дубль канала решается владельцем до T21.

Не трогай main.py, digest_*.py, планировщик v1, config.py. Тесты и линтер только из venv: ~/.venvs/unagi/bin/ruff check . и ~/.venvs/unagi/bin/python -m unittest discover -s tests.
