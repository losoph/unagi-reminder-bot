## 1. Продуктовые решения (приняты владельцем, не обсуждаются при исполнении)

- **Не парсить всё подряд.** Пагинация делается самым простым способом; ставка — на приоритизацию постов.
- **Каналы с < 20 постов в день — собирать всё.** Активнее порога — брать **топ-N по скору**,
  остальное отдавать строкой «ещё N постов» со ссылкой на канал.
- **Посты без текста (только медиа, без подписи) — выкидывать полностью**: не сохранять в `channel_posts`
  и не показывать. Заглушка «Медиа-файл…» из выпусков исчезает.
- Порог `20/день` и лимит `N` — параметры окружения, меняются без деплоя.
- **Форварды — главный сигнал ранжирования**, важнее реакций, ответов и охвата. Абсолютное число
  форвардов само по себе ничего не значит (зависит от подписчиков и среднего охвата), поэтому
  нормируется внутри канала. **Пост, у которого форварды выделяются на 25–50% выше нормы канала,
  обязан попасть в выпуск** — даже если он не вошёл бы в топ-N по общему скору.

**Обязательно учесть при снятии обрезки (регрессия, найдена при ревью плана):**

Минимум в рамках спринта:

  по умолчанию 1500–2000) — полный текст остаётся в `channel_posts`, урезается только рендер страницы;
- убрать молчаливый `pop()`: если очередной пост не помещается, добавить в конец страницы явную
  пометку об усечении и записать WARNING в лог с числом невошедших постов.
Нарезку выпуска на несколько страниц с индексом **не делать** — это `digest_editions` из раздела 4
(вне спринта).
**Тест:** выпуск, не влезающий в 60 КБ → ни один пост не исчезает бесследно, на странице есть пометка
об усечении, в логе WARNING с количеством невошедших постов.

### T4. Скоринг и отбор постов в выпуск
- Решение о наполнении выпуска принимается **по данным из БД**, без новых обращений к Telegram.
- Правило объёма: если у канала за период `< PRIORITIZE_THRESHOLD_PER_DAY` (по умолчанию 20) постов в день —
  включать все; иначе — топ-`MAX_POSTS_PER_CHANNEL` по скору + строка «ещё N постов» со ссылкой на канал.
- Скор: относительная метрика **внутри своего канала**, а не абсолютная (иначе крупные каналы забьют выпуск).
  Базово: `views` с поправкой на «зрелость» (свежий пост ещё не набрал просмотры) + доля реакций
  (`(reactions+3*forwards+2*replies)/views`) + свежесть. Ориентир формулы — `docs/research/email-digest.md` §2.1.
- **Холодный старт:** пока нет истории канала (нет медиан), использовать только долю реакций и свежесть,
  не делить на неизвестную медиану. Отсутствие метрик не должно выкидывать пост из выпуска.
- Скоринг — отдельный модуль без зависимостей от aiogram, чтобы покрывался юнит-тестами.

**Приоритет сигналов (обязательно к соблюдению):**

1. **Форварды — наибольший вес.** Считать долю пересылок на охват: `fwd_rate = forwards / max(views, 1)`,
   затем относительно нормы канала: `rel_fwd = fwd_rate / median_fwd_rate_30d(channel)`.
   Подписчиков использовать только как слабый приор, не как делитель основного сигнала.
2. **Просмотры** — с поправкой на «зрелость» (свежий пост ещё не добрал охват), тоже относительно медианы канала.
3. **Реакции** — меньший вес и обязательная деградация: на части каналов они отключены
   (`@telegram`) или вырождены в константу (`@trendmediachannel`, всегда 1). Отсутствие реакций
   не должно понижать пост.
4. **Ответы** (`replies`) — необязательный сигнал с минимальным весом, часто `None`.
5. **Свежесть** — как регулятор между «свежее» и «релевантнее».

Ориентировочные веса (параметры, подбираются на реальных данных, не хардкод):
`0.40*log2(1+rel_fwd) + 0.25*log2(1+rel_views) + 0.15*log2(1+rel_reactions) + 0.05*replies_signal + 0.15*freshness`.

**Правило обязательного включения:** если `rel_fwd >= FORWARD_STANDOUT_RATIO` (по умолчанию `1.25`),
пост включается в выпуск **сверх** лимита `MAX_POSTS_PER_CHANNEL`. Защита от всплеска:
не более `FORWARD_STANDOUT_MAX_EXTRA` (по умолчанию 3) таких постов на канал за выпуск;
при превышении берутся посты с максимальным `rel_fwd`, остальные уходят в хвост-строку.

**Холодный старт для этого правила:** пока нет медианы `fwd_rate` по каналу (мало истории),
правило обязательного включения не применяется — считать только общий скор. Не сравнивать с медианой
по всем каналам: на каналах с 8 тыс. и 112 тыс. подписчиков нормы несопоставимы.
**Готово:** для активного канала в выпуск попадает не более `MAX_POSTS_PER_CHANNEL` постов + хвост-строка;
для редкого канала — все посты.
**Тест:** канал с 50 постами за день → в выпуске ровно N и корректное «ещё 50-N»; канал с 5 постами → все 5.
**Тест (форварды):** канал с медианой `fwd_rate` 2% и постом с 3% (`rel_fwd=1.5`) → пост в выпуске,
даже если по общему скору он вне топ-N; при 5 таких постах в выпуск попадают 3 с максимальным `rel_fwd`.
**Тест (деградация):** канал с отключёнными реакциями → посты ранжируются по форвардам и просмотрам,
скор не нулевой.

- **T8.** Явная модель выполнения выпуска: на пользователя и период хранить запланированное время,

  Требование: курсор сканирования продвигается по фактически просмотренным постам; недоставленное
  остаётся в `channel_posts` как backlog; выпуск помечается `partial`; доставка идемпотентно
  дочитывает очередь в следующих циклах; при переполнении backlog — алерт и backpressure,
  посты не отбрасываются молча.

- **T10.** Управление алертами из самого сообщения: «Повторить сейчас», «Пауза 24 ч», «Пауза 7 дней»,
  «Отключить тех. алерты», «Настройки». Пауза алертов **не** останавливает дайджесты и retry.
- **T11.** Антиспам: дедуп по `user + period + scheduled_at`, cooldown, экспоненциальное снижение частоты;
  учитывать `TelegramForbiddenError`, чтобы не долбить остановившего бота.
- **T12.** Одно короткое recovery-уведомление, если пропущенный выпуск позже собран.
  Не отправлять, если алерты на паузе или выключены.
- **T13.** Watchdog фоновых задач: хранить время последнего успешного `digest_cycle`, одно служебное
  уведомление админу при простое цикла или растущем backlog. Пользователям это не дублируется.

## 4. Границы и запреты

- **Не** внедрять постоянный userbot с обработкой всех входящих сообщений.
- **Не** вызывать LLM на каждый пост: только батчем и только для кандидатов выпуска.
- **Не** трогать email-подсистему (рабочая) и MTProto-секреты.
- **Не** пушить в `main` без зелёного CI: `deploy.yml` требует `test` (docker build + `unittest discover -s tests`),
  push в `main` автоматически деплоит на прод.
- Секреты (`.env`, StringSession, msmtprc) не читать, не логировать, не переносить в репозиторий.
- Вне спринта (зафиксировано, не делать сейчас): GitHub-агрегация форков и звёзд, RSS-источники,
  `digest_editions` + FTS-поиск, папки с расписанием.
