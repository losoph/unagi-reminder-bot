# Исправление замечаний ревью DEP2

Ты работаешь в ветке этого worktree. Порядок:
1. `git fetch origin && git rebase origin/main` (ветка отстала от main; конфликты в docs/sprint/progress.md решай, оставляя оба блока). Если rebase упирается в чужие изменения — не переписывай их.
2. Для каждого пункта ниже сначала воспроизведи дефект (кратко), затем исправь минимально и добавь регрессионный тест, который падает на старом коде. Пункты, которые не подтверждаются, — пропусти и объясни в ответе.
3. Проверки: `~/.venvs/unagi/bin/ruff check .` и `~/.venvs/unagi/bin/python -m unittest discover -s tests` — всё зелёное. Тесты не ослаблять. Образ CI без git/jq: такие тесты через skipUnless.
4. Коммит локально, git push запрещён. Первая строка сообщения коммита должна заканчиваться маркером (DEP2-fix), например «fix: … (DEP2-fix)». Прогресс — файл docs/sprint/progress/DEP2-fix.md (не docs/sprint/progress.md).
5. Секреты не печатать и не коммитить. Область изменений — только эта задача.

## Отчёт независимого ревью (dsh)

обоих случаях `restarts` никогда не равен `0`, условие всегда истинно, и деплой завершается `exit
1`. **Сценарий:** любой деплой, дошедший до liveness, даже полностью здоровый: job краснеет,
`docker image prune`/`builder prune` не выполняются, а после merge с main не выполнится и
установка cron-файлов (они ниже блока). **Серьёзность: критическая (блокер).** Правильно: `docker
inspect -f '{{.RestartCount}}' unagi-bot`. 2. **`tests/test_dep2_deploy_verify.py:84-88` — тест
подыгрывает дефекту.** Фейковый `docker` отвечает `0` на любой шаблон, содержащий
`State.RestartCount`, то есть кодирует заведомо неверное поле. Реальный `docker inspect` в тестах
не запускается, хотя Docker в CI есть; `test_deploy_prune_does_not_use_all_flag` проверяет только
отсутствие `-a`, а `test_prod_check_inspects_git_sha_label` — лишь подстроку. **Сценарий:** 16/16
тестов зелёные, деплой всегда красный; зелёный suite не является доказательством
работоспособности. **Серьёзность: высокая** (маскирует блокер). 3.
**`.github/workflows/deploy.yml:67` — откатный тег берётся из `:latest`, а не из образа
работающего контейнера.** `latest` — это последний **собранный** образ, а не обязательно последний
**рабочий**. **Сценарий 17.10:** сборка прошла, `up` упал, контейнер остался на старом образе, но
`latest` уже указывает на новый. Следующая попытка деплоя делает `docker tag latest rollback` и
перезаписывает единственный known-good `:rollback` новым (возможно, нерабочим) образом; старый
хороший образ становится dangling и удаляется `image prune`. Откат приведёт не туда, куда
рассчитывали. Ошибка имени/отсутствия образа скрыта `2>/dev/null || true`. **Серьёзность:
высокая.** Лучше тегировать `$(docker inspect -f '{{.Image}}' unagi-bot)` или обновлять
`:rollback` только после успешного liveness. 4. **`.github/workflows/deploy.yml:67` + диск 9,8 ГБ
— `:rollback` навсегда задерживает предыдущий образ.** `docker image prune -f` не удаляет
тегированные образы, поэтому после каждого деплоя остаётся ещё один полный образ (python:3.12-slim
+ apt + pip-зависимости — сотни МБ, порядка 3–4 % диска). В main уже есть коммиты
`f808976`/`1fcb1c3`: диск прода 86 %, кеш сборки режут до 6 часов. **Сценарий:** следующий деплой
с rollback-тегом уходит за порог ALERT 85 % и ближе к заполнению; при дефекте №1 prune вообще не
запускается, и проблема усугубляется. Политики устаревания/удаления `:rollback` нет.
**Серьёзность: высокая (риск для прода).** 5. **`ops/aiqu/README.md:83-99` — инструкция отката
отключает новую проверку.** `docker compose up -d` вызывается до `git checkout` и без `export
GIT_SHA`, поэтому пересозданный контейнер получает метку `unknown`; `prod_check` печатает WARN
«первый деплой» и выходит с кодом 0 — защита от старого кода после отката выключена. Дополнительно
`git checkout <sha>` оставляет сервер в detached HEAD, а `prod_check` с дефолтным `--expect
origin/main` всё равно скажет «версия: на проде old, ожидалось new» — обещание README о
«согласованном HEAD» неверно, нужен `--expect <sha>`. **Сценарий:** успешный ручной откат, затем
проверка показывает WARN/ALERT и не подтверждает, что крутится именно откаченный код.
**Серьёзность: средняя.** 6. **`.github/workflows/deploy.yml:70-79` — liveness не сверяет метку
версии.** Проверяются только `State.Status` и `RestartCount`, а не `org.unagi.git_sha`.
**Сценарий:** `up` вернул 0, но Compose переиспользовал старый контейнер (повторный запуск того же
коммита/будущее изменение поведения) — job зелёный, хотя код старый; заявленная цель «деплой сам
замечает старый код» закрыта только ручным `prod_check`. Плюс `RestartCount == 0` корректен только
для заново созданного контейнера: у переиспользованного контейнера с прошлыми рестартами будет
ложное падение. **Серьёзность: средняя.** 7. **`ops/aiqu/prod_check.sh:62-66` — `PROD_CHECK_OUT`
превращает единственную разрешённую проверку прода в доверие произвольной строке.** При
установленной переменной SSH не вызывается вообще, проверка связи исчезает, можно напечатать
полностью зелёный отчёт без прода. **Сценарий:** случайно унаследованная/выставленная переменная в
оболочке или CI-обёртке «подтверждает» здоровье прода; тесты можно было сделать через фейковый
`ssh`/`docker` в `PATH`, как это уже сделано для deploy-блока. **Серьёзность: средняя/низкая**
(целостность проверки, не отказ прода). 8. **`ops/aiqu/README.md:83-112` — быстрый откат не
предупреждает про БД и миграции.** В операторской инструкции нет шага «восстановить снимок БД
перед деплоем», хотя `backup_db.py` его создаёт; в `progress/DEP2.md` это отмечено как
неидеальность, но в README — нет. **Сценарий:** деплой применил изменение схемы (или упал уже
после миграции), откатывается образ — старый код работает с новой БД; снимок есть, но инструкция
не говорит его использовать. Сейчас миграции заявлены аддитивными, поэтому риск ниже, но для
«быстрого отката» это существенно. **Серьёзность: средняя.** **Примечание по merge:** ветка
отстаёт от `origin/main` на 14 коммитов (`a0e17e1..738dd63`); `git merge-tree` показывает
изменение `deploy.yml` с обеих сторон, но **без конфликтов**. Однако в main уже есть disk-fix и
установка cron после liveness-блока — при дефекте №1 они не выполнятся, поэтому после merge нужен
повторный прогон и проверка на реальном Docker. **Вердикт: ЕСТЬ ЗАМЕЧАНИЯ.** П.1 — блокирующий: в
текущем виде деплой будет красным на каждом успешном `up`; п.3–4 делают откат и диск ненадёжными.
К слиянию и деплою без исправлений не готово.
