# Исправление замечаний ревью EXP1

Ты работаешь в ветке этого worktree. Порядок:
1. `git fetch origin && git rebase origin/main` (ветка отстала от main; конфликты в docs/sprint/progress.md решай, оставляя оба блока). Если rebase упирается в чужие изменения — не переписывай их.
2. Для каждого пункта ниже сначала воспроизведи дефект (кратко), затем исправь минимально и добавь регрессионный тест, который падает на старом коде. Пункты, которые не подтверждаются, — пропусти и объясни в ответе.
3. Проверки: `~/.venvs/unagi/bin/ruff check .` и `~/.venvs/unagi/bin/python -m unittest discover -s tests` — всё зелёное. Тесты не ослаблять. Образ CI без git/jq: такие тесты через skipUnless.
4. Коммит локально, git push запрещён. Первая строка сообщения коммита должна заканчиваться маркером (EXP1-fix), например «fix: … (EXP1-fix)». Прогресс — файл docs/sprint/progress/EXP1-fix.md (не docs/sprint/progress.md).
5. Секреты не печатать и не коммитить. Область изменений — только эта задача.

## Отчёт независимого ревью (dsh)

**`ops/aiqu/export_db.py:368-411` — пустая/чужая SQLite-БД проходит restore и затирает целевую.**
`PRAGMA quick_check` для пустой БД возвращает `ok`, `extract_db_meta` отдаёт 0 таблиц и fallback
`app_schema="utc_v1"`, схема с целевой `utc_v1` совпадает — `os.replace` заменяет боевую БД,
печатается `restore ok ... size=0`. Сценарий: экспорт не той/пустой БД либо подменённый `.age` с
`plaintext_size=0`; я воспроизвёл — цель с 2 таблицами стала 0 таблиц, код 0. Спасает только pre-
restore snapshot. — **Высокая.** 2. **`ops/aiqu/export_db.py:55-108` — «версия схемы» фактически
не проверяется.** `app_schema` берётся из `timestamps_storage` (`utc_v1`), а это флаг формата
времени, не версия схемы; в `data/database.py:161-179` нет сквозного версионирования, и на чистой
целевой БД код жёстко подставляет `"utc_v1"` (`export_db.py:401-404`). Экспорт с новыми
таблицами/колонками при том же `utc_v1` даст «равно» и не вернёт код 3. Тест
`test_schema_newer...` использует синтетический `utc_v2`, которого приложение никогда не пишет. —
**Высокая** (требование владельца не выполнено; при переезде с тем же коммитом риск ниже). 3.
**`ops/aiqu/export_db.py:308-316` — проверка WAL не гарантирует остановленный контейнер.** После
`PRAGMA wal_checkpoint(TRUNCATE)` у живого соединения `-wal` имеет размер 0, но остаётся `-shm`;
условие `st_size > 0` пропускает восстановление, затем `os.replace` и удаление `-wal`/`-shm`
(`451-457`) происходят под работающим ботом. Сценарий: забыли `docker compose stop`; бот
продолжает писать в старый inode/удалённый WAL — потеря/порча данных. — **Высокая.** 4.
**`ops/aiqu/README.md:110-160` — в порядке миграции нет остановки старого бота.** Новый раздел
ведёт «экспорт на старом → копирование → verify → restore на новом → запуск нового», но не требует
остановить старого бота перед финальным экспортом. Сценарий: записи после снимка теряются; старый
и новый боты одновременно поллят один токен (`Conflict`, потеря обновлений). В
`docs/roadmap.md:78-84` и чек-листе `ops/aiqu/README.md` шаг 6 это явно есть — раздел ему
противоречит. — **Высокая.** 5. **`ops/aiqu/export_db.py:111-153` — `format_version` не
проверяется.** Проверяется только наличие поля; `format_version: 2` (sha/size не менял) проходит
`verify` с кодом 0, `restore` тоже возвращает 0 — воспроизведено. Заголовок age проверяется только
по префиксу `age-encryption.org/`, а не по `v1`. Сценарий: будущий несовместимый формат молча
интерпретируется как v1. — **Средняя.** 6. **`ops/aiqu/export_db.py:217-255` — `export` доверяет
выводу `AGE_BIN` и не проверяет age-заголовок.** При `AGE_BIN=cat`/сломанной обёртке в
`storage/exports/*.db.age` пишется открытая SQLite-БД, скрипт печатает `export ok`; `verify` потом
вернёт 5, но plaintext уже на диске. Воспроизведено: файл начинается с `SQLite format 3`. —
**Средняя** (при подмене/ошибке `AGE_BIN` — высокая). 7. **`tests/test_export_db.py:197-222` —
тест «plaintext не остаётся» проверяет только export.** Именно `restore` пишет plaintext во
временный файл в целевом каталоге; нет теста, сканирующего каталог после
успешного/неуспешного/`--dry-run` restore на `*-restore-*.tmp` и sidecar-файлы. Также нет тестов
на пустую/чужую БД, на `format_version` и на реальный сценарий «новее схема при том же `utc_v1`».
Регрессия `finally`-уборки или проверки формата пройдёт CI. — **Средняя.** 8.
**`ops/aiqu/README.md:160-170` — «безопасно передавать через открытые каналы» переоценено.**
`sha256` лежит рядом с шифротекстом и не аутентифицирован; age шифрует на публичный ключ, который
доступен любому. Активный посредник может заменить `.age` и `.json` своим конвертом (например,
пустой БД из п.1), `verify` пройдёт, restore примет. Конфиденциальность защищена,
целостность/подлинность — нет. — **Средняя** (документация/модель угроз). 9.
**`.gitignore`/`.dockerignore` + `ops/aiqu/README.md:117-120` — экспорт попадает в git/Docker-
контекст.** Файлы пишутся в `storage/exports/` внутри репозитория и build context; `*.db` не
покрывает `*.db.age`/`*.db.age.json`. Сценарий: после экспорта `git add -A` коммитит ~10 МБ
шифрованного файла с манифестом, а следующий `docker compose up -d --build` на старом сервере
запекает его в слой образа (диск 9,8 ГБ, лишний объём, данные в образе). — **Средняя/низкая**;
можно обойти путём вне репозитория (`/root/exports`) или правкой ignore-файлов владельцем. 10.
**`ops/aiqu/export_db.py:176,238,374-378` — часть ошибок даёт traceback вместо кодов 1/2/5.**
Воспроизведено: `--out` указывает на существующий файл → `FileExistsError` из `out_dir.mkdir`;

`prod_check` считает их «свежим бэкапом». — **Низкая/средняя.** **Вердикт: ЕСТЬ ЗАМЕЧАНИЯ.**
Основная логика брифу соответствует (backup API в память, поток в stdin `age`, 0600, обязательный
