# Отчёт по безопасности Telegram-бота unagi

Режим: только чтение. Файлы не изменялись, коммиты не создавались, тесты не запускались. Все пункты проверены по коду (чтение + трассировка вызовов), номера строк — фактические.

## Список дефектов (по убыванию серьёзности)

**1. ВЫСОКАЯ — `main.py:2522-2531` + `data/database.py:2397-2425` — межпользовательский IDOR через `callback_data`**
`handle_alert_retry` берёт `execution_id` прямо из callback-данных и вызывает `retry_digest_execution(execution_id)`; в SQL нет ни `user_id`, ни сравнения с `callback.from_user.id` — `user_id` и `period` берутся ИЗ САМОЙ строки (`db:2401`), а затем `UPDATE subscriptions ... SET failure_count=0, digest_status='pending', is_disabled=0 WHERE user_id=? AND period=?` (`db:2418-2425`). Сценарий: любой пользователь, у которого есть хоть одно сообщение бота с inline-кнопкой (достаточно `/start`), отправляет своим MTProto-клиентом произвольный callback `alert_retry_1..N` (Telegram не проверяет, что `data` соответствует кнопке; id — AUTOINCREMENT) → у чужого пользователя стирается запись о сбое выпуска, сбрасываются счётчики ошибок, **принудительно включаются обратно отключённые подписки** и запускается внеплановая сборка дайджеста (нагрузка + спам-сообщение жертве). Исправление: `exec = get_digest_execution_by_id(execution_id)` и `if not exec or exec["user_id"] != callback.from_user.id: await callback.answer("Нет доступа", show_alert=True); return` (либо добавить `user_id` в `retry_digest_execution`).

**2. ВЫСОКАЯ — `data/database.py:1184` (+ `1267`, `3024-3029`) — нет лимита подписок на пользователя**
`add_subscription` просто INSERT-ит (проверки `COUNT` нет), тогда как в Ленте аналогичная защита есть: `db:3024-3029` (`>= MAX_FEED_CHANNELS → ValueError`). Импорт (`main.py:3418/3424/3566`) ограничен только размером файла 2 МБ и срезом 300 подписок **на файл** (`main.py:3467`), число импортов не ограничено, `channel_username` не проверяется на существование. Сценарий: `/import` одного и того же файла 100 раз → ~30 000 подписок; в цикле `get_due_subscriptions... → plan_due_editions (main.py:5326) → get_user_subscriptions_due_until (db:1267, без LIMIT) → prefetch_due_channels (main.py:5364)` все подписки одного пользователя грузятся в память и по каждой идёт сетевой запрос к t.me (семафор 5) → контейнер 512 МБ/1.5 CPU занят на часы, дайджесты остальных пользователей не доставляются. Исправление: в `add_subscription` проверять `SELECT COUNT(*) ... WHERE user_id=? AND is_disabled=0` против `MAX_DIGEST_SUBSCRIPTIONS`; добавить `LIMIT ?` в `get_user_subscriptions_due_until` и счётчик импортов в сутки.

**3. ВЫСОКАЯ — `main.py:3065-3088`, `4372-4396`, `3237-3247` — дорогие операции без кулдауна (усиление DoS)**
Ни в `main.py`, ни в роутерах нет middleware/anti-flood (проверено grep: `throttle|rate_limit|middleware` — пусто), при этом `/check` использует маркер «10 лет назад» (`main.py:3076`), поэтому в `scraper.get_latest_posts` не срабатывает ранний выход по курсору (`scraper.py:103-105`) и на каждый канал делается до `WEB_FETCH_MAX_PAGES=15` запросов (`scraper.py:23`, `189`, `217`); `/check` и `/test_digest` (`main.py:4393`) обходят **все** подписки пользователя, а `aiadj_` (`main.py:3244-3247`) тянет всю историю канала на каждое нажатие кнопки (лимит ИИ проверяется только для самого LLM-вызова, `main.py:3282`). Сценарий: пользователь с 300 подписками (см. п.2) шлёт `/check` в цикле → десятки тысяч исходящих запросов с IP сервера, FloodWait/бан у t.me, блокировка общего цикла. Для сравнения, в Ленте кулдаун есть: `feed.py:74, 927` (`FEED_MIN_INTERVAL_SECONDS=60`). Исправление: общий per-user cooldown (например, тот же приём, что в `feed.py:927`) для `/check`, `/test_digest`, `aich_/aiadj_/aisum_` + ограничение параллелизма.

**4. СРЕДНЯЯ — `main.py:4547-4574` — рассылка писем через SMTP бота на произвольные адреса**
`process_email_address` отправляет письмо с кодом на любой введённый адрес (`main.py:4563-4568`), ограничение — только 60 c между запросами одного пользователя (`main.py:4434, 4557-4560`), суточного/адресного лимита нет, состояние сохраняется уже ПОСЛЕ отправки. Сценарий: любой пользователь шлёт `/email` и раз в минуту указывает чужой адрес → ~1440 писем/сутки с SMTP-аккаунта сервера (репутация домена, жалобы на спам). Исправление: суточный лимит отправок на пользователя и на адрес (например, 5/сутки) до вызова `send_email`, плюс глобальный счётчик.

**5. СРЕДНЯЯ — `main.py:2239, 3068, 4375, 4484` против `2498, 3205, 4502`; `feed.py:801` — нет ограничения «только личный чат», идентичность = `chat.id`**
Фильтра `F.chat.type == PRIVATE` нигде нет (единственная проверка типа чата — `main.py:4618`, и та про `channel`), при этом часть обработчиков читает/пишет данные по `message.chat.id`/`callback.message.chat.id`, а часть — по `callback.from_user.id`. Сценарий: пользователь добавляет бота в группу и делает там `/save` (ответом на сообщение) или `/list`; chat.id = id группы, поэтому любой участник группы (в т.ч. добавленный позже) командой `/saved` читает тексты закладок и жмёт кнопки `rem_del_<id>` / `bkdel_<id>` / `unsub_<id>` на сообщениях бота, удаляя и изменяя данные, созданные другим человеком; при этом Лента (`from_user.id`) и дайджест (`chat.id`) начинают расходиться. Исправление: зарегистрировать `dp.message.filter(F.chat.type == ChatType.PRIVATE)` и такой же фильтр на callback (или middleware), а идентичность везде брать из `from_user.id`.

**6. СРЕДНЯЯ — `data/database.py:26-27` + `telegraph_publisher.py:51` — БД создаётся с правами 0644 и хранит токен Telegraph в открытом виде**
`sqlite3.connect(DB_PATH)` без `umask`/`chmod` (в репозитории chmod есть только для бэкапа — `ops/aiqu/backup_db.py:37`), `DB_PATH=storage/bot_data.db` (`docker-compose.yml:11` монтирует `./storage` на хост, контейнер работает от root с umask 022) → файлы `bot_data.db`, `-wal`, `-shm` доступны на чтение любому локальному пользователю. В `app_meta` лежит `telegraph_access_token` (`telegraph_publisher.py:51`, `data/database.py:2141`), а в `user_emails` — адреса и коды подтверждения. Сценарий: любой локальный аккаунт на VDS читает `storage/bot_data.db` → получает токен Telegraph, тексты приватных напоминаний/закладок, почту и коды. Исправление: `os.umask(0o077)` при старте + `os.chmod(DB_PATH, 0o600)` после первого подключения; токен Telegraph брать только из `TELEGRAPH_TOKEN`.

**7. СРЕДНЯЯ — `Dockerfile:1-20` + `docker-compose.yml:7, 15-20` — контейнер без изоляции: root + host network + секрет SMTP**
В Dockerfile нет `USER` (процесс — root), compose использует `network_mode: host` (нет сетевого периметра: доступны localhost-сервисы хоста), монтирует `/root/.msmtprc` с паролем SMTP и не ограничивает capabilities (`cap_drop`/`no-new-privileges`/`read_only` отсутствуют). Сценарий: RCE в боте (разбор недоверенного HTML/сообщений, зависимость) = root в хостовой сети и доступ к SMTP-паролю; при этом `mem_limit`/`cpus` заданы, т.е. часть изоляции сделана, а привилегии — нет. Исправление: `RUN useradd -u 10001 bot && USER bot`, убрать `network_mode: host` (боту достаточно исходящих), `read_only: true`, `cap_drop: [ALL]`, `security_opt: ["no-new-privileges:true"]`.

**8. СРЕДНЯЯ — `.github/workflows/deploy.yml:25` — непинованный сторонний action получает приватный SSH-ключ**
`uses: appleboy/ssh-action@master` с `secrets.SSH_KEY`, `secrets.HOST`, `secrets.USERNAME` (`deploy.yml:27-30`) — плавающий ref: force-push или компрометация апстрима даёт исполнение произвольного кода с ключом деплоя (затем `git pull origin main` + `docker compose up -d --build` в `~/projects/unagi-reminder-bot`, `deploy.yml:31-36`). Дополнительно: нет блока `permissions:` (токен workflow по умолчанию), нет environment/ручного подтверждения. Исправление: закрепить action по commit SHA (`appleboy/ssh-action@<sha>`), добавить `permissions: contents: read`, деплой отдельным непривилегированным пользователем.

**9. НИЗКАЯ-СРЕДНЯЯ — `data/database.py:809, 2236, 2065` + `main.py:2111, 3602, 3366-3390` — выборки без LIMIT при отсутствии квот**
`get_user_messages`, `get_saved_messages`, `export_user_data` читают все строки пользователя, пагинация делается в Python уже после загрузки; квот на число напоминаний/закладок нет (`add_message` — чистый INSERT, `db:747`; `add_saved_message` — `db:2207-2217`), импорт добавляет 1000 закладок и 500 напоминаний за прогон (`main.py:3510-3547`) и может повторяться. Сценарий: пользователь накапливает сотни тысяч строк, `/list`, `/saved` или `/export` грузят всё в память (плюс `PRAGMA temp_store = MEMORY`, `db:33`, и `cache_size = -64000`, `db:34`) → OOM контейнера 512 МБ (`docker-compose.yml:21`) и падение бота для всех. Исправление: `LIMIT`/SQL-пагинация и per-user квоты в `add_message`/`add_saved_message`.

**10. НИЗКАЯ — `main.py:991` и `main.py:998` (при `main.py:3468`, `data/database.py:84-87`) — HTML-инъекция в сообщениях Telegram**
Текст сообщения экранируется (`main.py:990`), а ссылка — нет: `f"🔹 <i>{text_safe}</i> <a href='{post['link']}'>[Читать]</a>"` и `f"▫️ <a href='https://t.me/{clean_user}'>..."`. `channel_username` при импорте не валидируется (`normalize_channel_username` только снимает `@` и приводит к lower case), поэтому JSON вида `{"channel_username": "x'><b>...</b><a href='https://evil.tld"}` выводит разметку из атрибута `href` и ломает/подменяет вёрстку дайджеста (а также позволяет обращаться к произвольным путям `https://t.me/s/<...>` в `scraper.py:186, 217` — хост фиксирован, поэтому это не SSRF). Исправление: `html.escape(value, quote=True)` для ссылок/username и валидация `^[A-Za-z0-9_]{4,32}$` перед сохранением подписки.

**11. НИЗКАЯ — `main.py:3520` → `main.py:3748` — импорт принимает произвольный `saved_at`, карточка закладки после этого не открывается**
`bookmark.get("saved_at")` пишется в БД как есть, а при открытии карточки вызывается `display_db_datetime(saved_at)` → `parse_db_datetime` → `datetime.strptime` (`data/database.py:46-49`). Сценарий: импорт с `"saved_at": "not-a-date"` → `ValueError` в обработчике при каждом открытии закладки (пользователь навсегда видит «Что-то пошло не так»). Исправление: валидировать дату через `parse_db_datetime` в try/except и подставлять `serialize_datetime(utc_now())`.

**12. НИЗКАЯ — `data/database.py:2907` (+ `424`, `2851`) — лимит попыток кода подтверждения почты обнуляется каждым повторным запросом**
В `start_email_verification` при `ON CONFLICT` выставляется `code_attempts = 0`, поэтому «5 попыток» (`db:2925`) не мешают перебору: запрос нового кода раз в 60 c (`main.py:4434, 4557-4560`) сбрасывает счётчик. Сценарий: злоумышленник перебирает 6-значный код по 5 попыток в минуту бесконечно (код при этом лежит в БД в открытом виде — см. п.6). Исправление: не сбрасывать `code_attempts` при переотправке (обнулять только после `ok`) и хранить хэш кода.

**13. НИЗКАЯ — `data/database.py:586-588` + `1188-1196` — уникальный индекс подписок пересоздаётся на каждом старте, а `add_subscription` не транзакционен**
`init_db` делает `DROP INDEX IF EXISTS uq_subscriptions_user_channel_period_active` и создаёт индекс заново (`db:720-726`), а `add_subscription` выполняет SELECT-затем-INSERT без `BEGIN IMMEDIATE` (в отличие от `add_feed_subscription`, `db:3013-3014`). Сценарий: перекрытие деплоя/двух параллельных запросов создаёт дубли активных подписок → дублирующиеся дайджесты (в пределах одного пользователя, без межпользовательского влияния). Исправление: не удалять индекс при каждом старте и обернуть `add_subscription` в `BEGIN IMMEDIATE`/`INSERT ... ON CONFLICT`.

**14. НИЗКАЯ — `data/database.py:1670` — `get_channel_posts_since` без LIMIT, хотя вызывающий берёт 50 строк**
`main.py:1188-1193` режет результат до `CHANNEL_DELIVERY_BATCH_SIZE`, но из БД вычитывается весь backlog канала (память/`temp_store = MEMORY`). Исправление: `LIMIT ?` с размером батча в оба запроса функции.

## Вердикт

По проверенным классам: **SQL-инъекций нет** — все запросы параметризованы, динамических имён таблиц/колонок нет, `executescript`/`load_extension`/`ATTACH` отсутствуют. **SSRF нет** — хосты исходящих запросов жёстко заданы (`t.me`, `api.telegra.ph`, `api.deepseek.com`), SMTP/прокси берутся только из env; из непроверенного ввода строится лишь путь на фиксированном хосте (п.10). **XXE нет** — XML не парсится, HTML разбирается `html.parser`. **Утечек секретов в логи нет** — `BOT_TOKEN`, `DEEPSEEK_API_KEY`, `TELEGRAM_USER_SESSION`, SMTP-пароль не логируются (единственное — `ai_assistant.py:54` пишет 300 символов тела ответа провайдера, куда может попасть пользовательский текст). Экспорт/импорт JSON строго привязан к `user_id` вызывающего, path traversal в файловых операциях нет (файл читается из Telegram в память, имя не используется как путь).

Реальные проблемы лежат не в SQL, а в **отсутствии слоя авторизации, квот и троттлинга**: один пользователь может изменить состояние дайджеста другого (п.1), уложить бота ресурсами (п.2, 3, 9) и использовать SMTP сервера для рассылки (п.4); усугубляют картину общий аккаунт в группах (п.5), права файлов БД вместе с токеном Telegraph (п.6), непривилегированный контейнер без изоляции (п.7) и непинованный action с SSH-ключом (п.8).

## 3 самых срочных пункта

1. **П.1** — проверка владельца в `handle_alert_retry`/`retry_digest_execution` (`main.py:2531`, `data/database.py:2397`): единственная найденная межпользовательская запись по чужому id, эксплуатируется тривиально.
2. **П.2 + П.3** — квота подписок в `add_subscription` (`data/database.py:1184`) и общий per-user кулдаун для `/check`, `/test_digest`, `aiadj_` (`main.py:3065, 4372, 3237`): без них любой один пользователь останавливает доставку дайджестов всем.
3. **П.8 (+ П.7)** — закрепить `appleboy/ssh-action` по SHA и убрать root/host-network у контейнера (`deploy.yml:25`, `Dockerfile`, `docker-compose.yml:7`): это цепочка «RCE в боте → root на хосте + ключ деплоя», цена ошибки здесь максимальная.
