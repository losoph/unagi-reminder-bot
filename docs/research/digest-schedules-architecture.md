# Несколько выпусков на период и разделение подписок по времени: варианты архитектуры

Дата: 2026-10-10. Статус: **решение принято** — модель «папка → расписания → выпуск» (вариант B с отдельной сущностью расписания), см. [roadmap.md](../roadmap.md) §2.

## Запрос

1. Несколько ежедневных, еженедельных и ежемесячных дайджестов у одного пользователя
   (например «Новости» в 8:00 и 19:00 по будням, «Длинное чтение» по субботам).
2. Подписки делятся по времени выпусков; теги (папки) остаются и дополняют это деление.
3. Доставка выпуска **эксклюзивна**: либо почта, либо Telegram (решено, «оба» не делаем).

## Продуктовые рамки (решено 2026-10-10)

- unagi остаётся Telegram-ботом: напоминания, закладки, дайджесты каналов в чат/Telegraph.
- **ghsub развивается как многопользовательский агрегатор источников в почту** (ранжирование,
  важность, типология; GitHub — первый из источников). Почтовое дайджестирование
  Telegram-каналов **позже переезжает из unagi в ghsub**.
- Общие библиотеки/БД — только как профиль развёртывания на сервере aiqu, не как слияние продуктов.

Следствие: модель расписаний должна быть **переносимой** — та же сущность «выпуск» понадобится ghsub,
а почтовая ветка unagi — временная.

## Текущее состояние кода

- `subscriptions(period, next_send_at, tag, last_post_id, …)` — период и курсор доставки на подписке.
- `digest_settings(user_id, period → send_hour, send_minute, weekday, month_day, monthly_mode)`,
  PK `(user_id, period)` — один выпуск на период.
- `user_emails.email_periods` — список периодов, идущих на почту.
- `digest_executions` и `digest_alerts` ключуются `(user_id, period, scheduled_at)`.
- Канальные посты общие (`channel_posts`), курсор сканирования — на канале, курсор доставки —
  `subscriptions.last_post_id`.
- UI: inline-кнопки, `main.py` ≈ 219 КБ (монолит).

## Варианты

### A. «Выпуск» как сущность, теги — фильтр (many-to-many)

```
editions(id, user_id, name, schedule: kind daily|weekly|monthly|cron + slots, delivery email|telegram,
         tag_filter, next_send_at, …)
edition_cursor(edition_id, subscription_id, last_post_id)   -- курсор на пару
```
Канал может попасть в несколько выпусков (по тегам). Ключ executions/alerts → `edition_id + scheduled_at`.

- Плюсы: максимальная гибкость; совпадает с моделью «pipe» в goeland и группами ghsub;
  легко переносится в ghsub как есть.
- Минусы: курсор доставки множится (subscription × edition); дубли постов между выпусками
  (нужно правило «пост уже доставлен в другом выпуске сегодня?»); сложнее объяснить в UI
  («почему канал пришёл дважды»).

### B. Папка (тег) = расписание, у папки 1..N слотов

```
folders(id, user_id, name, schedule kind + slots[], delivery, next_send_at)
subscriptions.folder_id   -- одна папка на подписку; «Без папки» = дефолтное расписание
```
Выпуск = (папка, слот). Курсор остаётся на подписке.

- Плюсы: канал в одном месте → нет дублей; курсор не множится; UI «папка → ⏰ Расписание»;
  миграция: текущий `tag` → `folder`, текущий `period` → дефолтный слот.
- Минусы: тег перестаёт быть свободной меткой (одна папка на канал); если нужен канал и в
  утреннем, и в недельном выпуске — нельзя (или через `period_override` на подписке).

### C. Несколько слотов на период, подписка привязана к слоту

```
digest_slots(id, user_id, period, send_hour, send_minute, weekday, month_day, delivery)
subscriptions.slot_id
```
- Плюсы: наименьшая миграция; не трогает теги.
- Минусы: «разделение по времени» не связано с тегами — пользователь вручную раскладывает
  каждый канал по слотам; для ghsub не переносится как понятие.

### D. Гибрид: B + необязательные «сборные выпуски»

Основа как в B (папка с расписанием, одна папка на подписку, курсор на подписке). Отдельно —
редкий «сборный» выпуск (например месячный обзор всех папок), который читает **уже доставленные**
посты (`digest_edition_items`) и не двигает курсоры. Это же даёт основу под «выпуск целиком
в Закладки/Отложенные» из roadmap.

- Плюсы: простое ядро без дублей + гибкость «обзоров» без второго курсора.
- Минусы: два типа выпусков; сборный выпуск зависит от snapshot-таблицы, которой пока нет.

## Сквозные вопросы для любого варианта

1. Ключ `digest_executions` / `digest_alerts`: `(user, period, scheduled_at)` → `(edition|folder_slot, scheduled_at)`;
   миграция существующих строк.
2. Эксклюзивность доставки — на уровне выпуска; `user_emails.email_periods` → поле `delivery` выпуска.
3. Делать ли почтовую доставку новых выпусков в unagi сейчас, если почта затем переезжает в ghsub?
   (вариант: в unagi сейчас только Telegram-выпуски по новой модели, email оставить по-старому
   на `period`, новую почту сразу строить в ghsub).
4. Интерфейс обмена unagi → ghsub при переезде почты: ghsub читает `channel_posts` из SQLite unagi
   (только на aiqu-профиле), или unagi отдаёт выпуск в виде JSON-секции.
5. Планировщик: переход на «спать до ближайшего `next_send_at`» становится важнее при множестве слотов.
6. Разбиение `main.py` (handlers/keyboards/services) до или вместе с UI расписаний.

## Итог ревью (Claude + opencode/gpt-5.6-sol, 2026-10-10)

- Выбран **B с отдельной сущностью расписания**: `folders` (из `tag`) → `digest_schedules` (1..N на
  папку, `delivery` у расписания) → `digest_editions` + `digest_edition_items` (snapshot до отправки).
- Канал — строго в одной папке; курсор на подписке. Несколько расписаний одной папки делят поток
  по времени (утренний выпуск забирает ночные посты, вечерний — дневные), курсор не множится.
- Найденные риски текущего кода: доставка не идемпотентна на уровне выпуска (падение между
  отправкой и сдвигом курсора → повтор тех же постов); `scheduled_at` execution берётся из первой
  due-подписки — при нескольких слотах это даёт неверную группировку. Лечится snapshot'ом и
  выбором due-расписаний вместо due-подписок.
- `digest_executions`/`digest_alerts` → ключ `schedule_id + scheduled_at`; старая история — legacy.
- Сквозной вопрос 3: новую email-доставку в unagi не строим; существующие email-периоды мигрируют
  в дефолтные расписания с `delivery=email` и живут до переезда в ghsub (ghsub ADR-006).
- Сквозной вопрос 4: контракт unagi → ghsub — версионированный JSON выпуска с идемпотентным
  `edition_id`, без общей SQLite.
- Пропуски из-за простоя — один объединённый catch-up выпуск на расписание.
