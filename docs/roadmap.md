## 0. Границы продукта (решено 2026-10-10)

- **unagi — Telegram-бот**: напоминания, закладки, дайджесты каналов в чат и Telegraph.
- **Почтовое дайджестирование уходит в [ghsub](https://github.com/losoph/ghsub)**, который
  развивается как многопользовательский агрегатор источников в почту (GitHub — первый источник,
  Telegram-каналы unagi — один из следующих). См. ghsub `docs/adr/ADR-006`.
- Слияния кодовых баз нет (ADR-005 в ghsub заменён ADR-006). Общие библиотеки и ресурсы —
  только как профиль развёртывания на сервере aiqu.
- Текущая email-доставка unagi (`/email`, выбор почта/Telegram на период) **сохраняется как есть
  до переезда**, новыми возможностями не расширяется.
- **Уточнение 2026-10-12.** Единственное исключение — ссылки «Отписаться/Перенести» под каждым
  каналом в письме (сделано 12.10). **Лента** (§1a) — только Telegram и Telegraph; Лента на почту —
  в ghsub по контракту выпуска. Роли проектов, кандидаты в ghsub и схема совместной работы на
  одном сервере — [research/ghsub-candidates.md](research/ghsub-candidates.md).

## 2. Очередь 4: несколько расписаний дайджестов на папку

Варианты и ревью — [research/digest-schedules-architecture.md](research/digest-schedules-architecture.md).
Выбрана модель **папка → расписания → выпуск**:

- текущий `tag` подписки мигрирует в `folders`; канал состоит **строго в одной папке**,
  курсор доставки остаётся на подписке (нет дублей между выпусками);
- у папки 1..N `digest_schedules` (daily/weekly/monthly + время), доставка у расписания
  эксклюзивна; новые расписания — только Telegram, существующие email-периоды мигрируют
  в дефолтные расписания с `delivery=email`;
- `digest_editions` + `digest_edition_items` — snapshot выпуска до отправки, повторы идут
  по тому же snapshot (идемпотентность), курсоры двигаются после доставки;
- `digest_executions` / `digest_alerts` переходят на ключ `schedule_id + scheduled_at`;
  старая история сохраняется как legacy, без угадывания соответствий;
- пропуски из-за простоя — **один объединённый catch-up выпуск** на расписание;
- планировщик выбирает due-**расписания**, а не due-подписки; затем — сон до ближайшего
  `next_send_at` вместо опроса раз в 30 минут;
- миграция с backup и dry-run-отчётом.

На этой же основе делается «выпуск целиком в Закладки/Отложенные» (см. §5).

## 3. Очередь 5: резервная доставка в MAX

- При исчерпании `MAX_MESSAGE_RETRIES` из-за **сетевых** ошибок Telegram напоминание
  уходит в MAX текстом (из §1.1) с пометкой источника. `Forbidden`, дайджесты и админ-алерты
  в MAX не дублируются.
- Транспорт — userbot `pymax` (как в losoph/maxfwd). Привязка MAX-чата к пользователю.
- Сессия/номер MAX — секрет вне репозитория, с политикой эксплуатации как у MTProto (§4.2).

## 4. Эксплуатация

0. **Переезд на российский сервер** (решение 2026-10-11): telemt на зарубежном IP из России не
   работает. Перенос unagi, ghsub и telemt со всеми настройками и харденингом, плюс
   OVPN-туннель до Telegram DC. Чек-лист — [ops/aiqu/README.md](../ops/aiqu/README.md).
   Харденинг текущего сервера выполнен 2026-10-11 там же.
1. **Экспорт зашифрованной базы для переноса между серверами.** Админская операция: консистентный
   snapshot, сразу шифруется публичным recovery-ключом (например, `age`), отдаётся только
   непрозрачный файл с checksum/версией формата. Приватный ключ хранится вне сервера. На новом
   сервере — offline-restore с проверкой checksum, версии схемы и обязательным backup текущей БД.
   Plaintext snapshot во временных каталогах не оставлять, шифровать потоково, журналировать
   только факт/размер/хеш. Граница гарантии: root исходного сервера технически может прочитать
   live-БД; схема защищает экспортируемый файл.
2. **Политика эксплуатации MTProto-session** (и далее MAX-сессии). Задокументировать владельца
   сервисного номера, включить 2FA, хранить session вне репозитория, проверить процедуру
   отзыва/перевыпуска без потери Bot API-доставки.
3. **Пользовательский экспорт своих данных** развивать отдельно от серверного encrypted backup.

## 5. Продуктовый backlog

### Экспорт/импорт
- **Импорт OPML.** Списки каналов в формате OPML (`<outline xmlUrl="https://t.me/s/channel">`)
  для переноса подписок из RSS-читалок и Telegram-RSS-ботов; период по умолчанию.

### Дайджесты
- **Выпуск целиком в Закладки/Отложенные.** Действия у заголовка выпуска относятся ко всему
  выпуску («Открыть полностью», «В Закладки», «Напомнить»), даже если он разбит на несколько
  сообщений. Опирается на `digest_editions` из §2:
  - стабильная Telegraph-сводка (весь текст, названия каналов, ссылки на исходные посты);
    закладка хранит название/дату и URL, повторное нажатие не создаёт дублей;
  - если выпуск превышает лимит Telegraph — набор страниц и одна индексная;
  - в Telegraph не попадают user ID, настройки, ошибки и прочий приватный контекст;
  - нормализованный состав хранится в БД для повторной публикации при смене токена;
  - выпуск в Закладках или будущих Отложенных не удаляется 30-дневной очисткой;
  - для маленького выпуска Telegraph создаётся лениво, для большого переиспользуется.
- **Управление каналами внутри Telegraph-дайджеста.** В больших выпусках теряются
  «Отписаться/Перенести» по каналу — нужен компактный аналог.
- **Keyword-фильтры на подписку** (include/exclude) — борьба с рекламой без ИИ
  (эвристики — research/email-digest.md, Приложение A.2).
- **Preview перед подпиской** — последние N постов канала до подписки.
- **Глобальное расписание по умолчанию** для новых подписок («Без папки») — часть §2.

### Почта (переезжает в ghsub)
- RSS-фиды, сайты без RSS, почтовые механики, команды из письма — вход для ghsub:
  [research/email-digest.md](research/email-digest.md) и
  [research/ghsub-candidates.md](research/ghsub-candidates.md) (G1–G18). Ранжирование «лентой»
  для Telegram-каналов делается в unagi (§1a); со стороны unagi для почты нужен только контракт
  выдачи выпуска (JSON v1, `ghsub-candidates.md` §2.2, ghsub ADR-006).

### DeepSeek / база знаний
- **Кросс-канальные заготовленные вопросы**: «Топ-5 главных за неделю/месяц» по всем подпискам.
- **Кэширование саммари** по каналу за период.
- **Расширить ручной `/check` диагностикой**, не превращая его в поток периодических сообщений.

## 6. Технический долг

Из аудита кода от 15.09.2026 и спринта 17.10.2026:

- **Распил монолита `main.py`**: кластеры закладок (`bookmarks.py`, MS1) и настроек дайджеста (`digest_settings.py`, MS2) вынесены в Router с проверкой через `tools/handler_order.py`. Осталось вынести:
  - мастер оформления подписки `setup_digest`;
  - экспорт и импорт данных (`/export`, `/import`);
  - фоновые циклы доставки и обработчики технических алертов;
  - реестр клавиатур и экранов FSM.
- **Синхронный доступ к SQLite в event loop**: `get_connection()` очищен от избыточных PRAGMA и chmod, очистка переведена на батчи (DB1). Осталось: вынос тяжелых синхронных запросов к БД в `asyncio.to_thread` / пул потоков для предотвращения задержек в цикле событий.
- **HTTP-сессии на каждый запрос** в `ai_assistant.py`, `telegraph_publisher.py`, `scraper.py` — один общий `aiohttp.ClientSession`.
- **Разрозненный `os.getenv`** в четырёх модулях — кандидат `pydantic-settings`.
- **`render_screen` — цепочка `if/elif`** по именам экранов → реестр обработчиков.
