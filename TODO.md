### Отложенное подключение MTProto

MTProto нужен только для более надёжного нативного чтения истории публичных
каналов. Bot API не умеет получать историю произвольного канала. Без MTProto бот
остаётся работоспособным: `CHANNEL_SOURCE=auto` автоматически использует
Telegram Web, если MTProto-секреты не заданы.

#### 1. Создать Telegram API-приложение

1. Войти техническим сервисным аккаунтом на <https://my.telegram.org>.
2. Открыть **API development tools**.
3. Заполнить форму:
   - **App title:** `Unagi Digest`;
   - **Short name:** уникальное имя из 5–32 латинских букв и цифр, например
     `unagidigest2607`;
   - **URL:** `https://github.com/losoph/unagi-reminder-bot`;
   - **Platform:** `Desktop`;
   - **Description:** `Telegram client for collecting public channel posts and creating user digests`.
4. Сохранить полученные `api_id` и `api_hash` в менеджере секретов. Не добавлять
   их в Git и не присылать в чат или на скриншотах.

Если форма показывает пустой `ERROR`: проверить полноценный `https://` URL,
выбрать новое уникальное Short name, убрать нестандартные символы, попробовать
приватное окно/другой IP и при необходимости повторить позже — Telegram может
временно запрещать создание приложения без объяснения.

#### 2. Один раз создать пользовательскую StringSession

`api_id` и `api_hash` идентифицируют приложение, но сами по себе не авторизуют
технический Telegram-аккаунт. `StringSession` — сохранённая авторизация этого
аккаунта. Она позволяет серверу читать каналы после перезапуска без повторного
ввода SMS-кода и 2FA.

Session генерируется один раз в доверенном локальном терминале:

```bash
cd /Users/adm/Documents/unagi
.venv/bin/python scripts/generate_mtproto_session.py
```

Здесь `.venv/bin/python` — путь к уже существующему Python-интерпретатору
проекта, а `scripts/generate_mtproto_session.py` — запускаемый им скрипт.
Команда не создаёт «пустой Python», новое окружение или новый Telegram-аккаунт.
Скрипт попросит `api_id`, `api_hash`, номер технического аккаунта, одноразовый
код Telegram и 2FA-пароль, а затем выведет `StringSession`.

Если локального `.venv` ещё нет, сначала создать его и установить зависимости:

```bash
cd /Users/adm/Documents/unagi
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Новую session нужно создавать только при отзыве/утере текущей session, смене
технического аккаунта или принудительном завершении его Telegram-сессий.
`StringSession` предоставляет доступ к аккаунту и является самым чувствительным
из этих секретов.

#### 3. Добавить секреты в `.env` production-сервера

```bash
ssh tender-ru
cd ~/projects/unagi-reminder-bot
nano .env
```

Добавить или обновить:

```dotenv
CHANNEL_SOURCE=auto
TELEGRAM_API_ID=<api_id>
TELEGRAM_API_HASH=<api_hash>
TELEGRAM_USER_SESSION=<StringSession>
MTPROTO_WEB_FALLBACK=true
MTPROTO_FETCH_LIMIT=1000
```

Не использовать `echo ... >> .env` с секретами: они могут попасть в shell
history. `.env` уже исключён из Git и не должен публиковаться в GitHub.

#### 4. Перезапустить Docker и проверить MTProto

```bash
cd ~/projects/unagi-reminder-bot
docker compose up -d --force-recreate bot
docker compose ps
docker compose logs --since 5m bot
```

В журнале должна появиться строка `Channel source: MTProto user ...`. Если
авторизация не прошла, при `CHANNEL_SOURCE=auto` и
`MTPROTO_WEB_FALLBACK=true` бот продолжит работать через Telegram Web.
После проверки выполнить `/test_digest` в боте и убедиться, что в логах для
каналов появляются строки `MTProto channel ... produced ... new posts`.

## Приоритет сразу после MTProto: стабильность и алерты

1. **Явная модель выполнения регулярного дайджеста.** Для каждого пользователя
   и периода хранить запланированное время, начало/конец попытки и итог:
   `delivered`, `empty` (каналы прочитаны, новых постов действительно нет),
   `partial`, `retrying` или `failed`. Не считать отсутствие сообщения
   пользователю ошибкой, если все каналы успешно проверены и новых постов нет.
2. **Пользовательский алерт о действительно пропущенном дайджесте.** Отправлять
   его только после grace period и исчерпания автоматических повторов, а не при
   первой сетевой ошибке. Один агрегированный алерт должен объяснять, какой
   daily/weekly/monthly выпуск не сформирован, сколько каналов недоступно и будет
   ли ещё одна попытка. Не слать отдельное сообщение на каждый канал.
3. **Управление техническими алертами прямо из сообщения.** Добавить кнопки:
   «Повторить сейчас», «Пауза алертов на 24 часа», «На 7 дней»,
   «Отключить тех. алерты» и «Настройки». Пауза/отключение алертов не должны
   останавливать сами дайджесты и автоматические retry. В настройках нужна
   отдельная кнопка повторного включения и видимый текущий статус.
4. **Антиспам и защита от постоянного mute/stop бота.** Дедуплицировать алерты
   по `user + period + scheduled_at`, установить cooldown и экспоненциальное
   снижение частоты при длительном сбое. После первого алерта обновлять его или
   присылать только итог восстановления; не повторять одинаковое предупреждение
   каждые 30 минут. Учитывать `TelegramForbiddenError`, чтобы не пытаться
   бесконечно уведомлять остановившего бота пользователя.
5. **Уведомление о восстановлении.** Если пропущенный выпуск позже успешно
   собран, прислать один короткий recovery-статус и ссылку на дайджест. Не
   отправлять recovery, если пользователь поставил технические алерты на паузу
   или выключил их.
6. **Watchdog фоновых задач и уведомление админу.** Хранить время последнего
   успешного `digest_cycle` и отправлять одно служебное уведомление, если цикл
   давно не завершался или backlog растёт несколько запусков подряд. Это
   отдельный инфраструктурный алерт и он не должен дублироваться всем
   пользователям.
7. **Отделить регулярный ingestion от времени доставки.** После активации
   MTProto синхронизировать каждый уникальный канал по собственному курсору,
   независимо от пользовательских daily/weekly/monthly задач. Delivery должен
   только выбирать уже сохранённые `channel_posts`; это уменьшит задержку,
   позволит повторить отправку без повторного обращения к Telegram и даст
   точный ответ, был ли выпуск `empty` или сбор действительно не состоялся.
8. **Самовосстановление Telegraph-токена.** Production уже возвращал
   `ACCESS_TOKEN_INVALID`; доставка не пропала благодаря fallback на Telegram,
   но большие дайджесты разбились на сообщения. При этой конкретной ошибке
   удалить невалидный token, один раз создать новый и повторить публикацию.
9. **Автоматический резервный снимок SQLite перед deploy.** Копировать
   консистентный snapshot через SQLite backup API в отдельный каталог с
   ротацией, затем выполнять `git pull`/пересборку. Не архивировать live-файл
   простым `cp` во время записи WAL.
10. **Экспорт зашифрованной базы для переноса между серверами.** Добавить
    отдельную админскую операцию, которая создаёт консистентный SQLite snapshot,
    сразу шифрует его публичным recovery-ключом (например, `age`) и отдаёт только
    непрозрачный файл с checksum/версией формата. Приватный ключ расшифровки
    хранить вне исходного сервера и не выдавать оператору экспорта; тогда админ
    может скачать и перенести архив, не читая из него пользовательские
    подписки, закладки и напоминания. На новом сервере предусмотреть отдельную
    offline-команду restore с проверкой checksum, версии схемы и обязательным
    backup существующей БД перед заменой. Не оставлять plaintext snapshot во
    временных каталогах; по возможности шифровать потоково, ограничить права
    файла и журналировать только факт/размер/хеш экспорта без пользовательских
    данных. Граница гарантии: root-администратор работающего исходного сервера
    технически способен прочитать live-БД; эта схема защищает содержимое
    экспортируемого файла и исключает хранение ключа расшифровки на сервере.
11. **Политика эксплуатации MTProto-session.** Задокументировать владельца
   сервисного номера, включить 2FA, хранить session отдельно от репозитория и
   проверить процедуру отзыва/перевыпуска без потери Bot API-доставки.

## Проверено и закрыто в июле 2026

- **Runtime-метрики дайджестов — реализовано.** Каждый цикл пишет одну
  структурированную строку `digest_cycle`: общий due/backlog, обработанный batch,
  число каналов и полученных постов, успешные доставки, ошибки и длительность.
  Фоновая очистка уже логирует количество удалённых записей.
- **Batch-limit due-подписок — реализовано как предохранитель, не как текущее
  ускорение.** `DIGEST_DUE_BATCH_SIZE=100`, сортировка по `next_send_at, id`
  гарантирует обработку самых старых подписок без starvation; оставшийся backlog
  продолжает обрабатываться через 5 секунд, а не через обычные 30 минут. На
  момент проверки в production было 45 активных подписок, поэтому лимит обычно
  не задействован.
- **Ручной `VACUUM` — признан неактуальным и не реализован.** На момент проверки
  production SQLite занимала около 0,95 МБ, `freelist_count=0`; команда не
  освободила бы место, зато могла бы блокировать рабочую БД. Вернуться к вопросу
  только при измеримой фрагментации или существенном росте файла.

## Продуктовый backlog после задач надёжности

### Экспорт/импорт
- **Полный текст напоминаний в экспорте.** Сейчас `scheduled_messages` хранит только `text_preview` (~40 символов), поэтому экспортированные напоминания теряют полный текст. Чтобы экспорт был lossless — хранить полный текст напоминания в БД.
- **Импорт OPML** (уже отмечено в README). Поддержать импорт списков каналов в формате OPML (`<outline xmlUrl="https://t.me/s/channel">`) для переноса подписок из RSS-читалок и других Telegram-RSS-ботов; период ставить по умолчанию.

### Дайджесты
- **Управление каналами внутри Telegraph-дайджеста.** Сейчас в больших дайджестах (Telegraph) теряются inline-ссылки «Отписаться/Перенести» по каждому каналу — остаётся только ссылка на «Настройки дайджеста». Добавить компактное управление каналами для Telegraph-версии.
- **Discovery: отмеченные посты и «вернуться к выбранному».** Проверить, нужна
  ли пользователю inline-команда рядом с постом/заголовком дайджеста для
  добавления отдельных записей в отложенную выборку, а затем единая настройка,
  когда напомнить о выбранном. Не создавать новую вложенную сущность до
  проверки сценария. Предпочтительный MVP: действие «Отметить» сохраняет
  `channel + post_id + link + preview` в существующую базу знаний с системным
  тегом «Из дайджеста», а «Вернуться» использует существующий механизм
  напоминаний (`вечером`, `завтра`, точная дата). Добавить экран
  «Отмечено из дайджестов» с массовыми действиями: напомнить, снять отметки,
  перенести в обычную папку.

  Перед реализацией проверить:
  - достаточно ли пользователям обычных закладок и индивидуального напоминания;
  - нужна ли одна дата на всю подборку или разные даты для каждого поста;
  - должна ли отметка переживать удаление/редактирование исходного поста;
  - как показать действие в Telegraph, где бот не может добавить Telegram
    callback-кнопку непосредственно к каждому элементу страницы;
  - как дедуплицировать повторно отмеченный `channel + post_id`;
  - нужен ли отдельный digest/экран выбранного или достаточно существующей базы
    знаний.

  Отдельную сущность `digest_collections` вводить только если подтвердятся
  групповые сценарии: именованные подборки, общий срок, совместные массовые
  действия или несколько независимых очередей чтения. Иначе это лишняя
  вложенность поверх `channel_posts`, `digest_posts`, `saved_messages` и
  `scheduled_messages`.
- **Keyword-фильтры на подписку** (include/exclude) — пропускать/прятать посты по стоп-словам (борьба с рекламой/мусором без ИИ). Из исходного списка заимствований (п.4), пока не реализовано.
- **Preview перед подпиской** — при пересылке поста показывать последние N постов канала, чтобы оценить частоту до подписки.
- **Глобальная периодичность по умолчанию** для новых подписок (выбор дефолтного периода/времени), в дополнение к пошаговой настройке после подписки.

### DeepSeek / база знаний
- **Кросс-канальные заготовленные вопросы**: «Топ-5 главных за неделю/месяц» по всей базе подписок (сейчас анализ только по одному каналу).
- **Кэширование саммари** по каналу за период, чтобы не тратить токены на повторные одинаковые запросы.
- **Расширить ручной `/check` диагностикой**, но не превращать его в отдельный
  поток периодических сообщений: автоматические проблемы должны агрегироваться
  механизмом пользовательских алертов выше.

### Эксплуатация
- **Пользовательский экспорт своих данных** развивать отдельно от серверного
  encrypted backup: пользователь получает только собственные записи, а
  переносимый админский архив остаётся целиком зашифрованным.
