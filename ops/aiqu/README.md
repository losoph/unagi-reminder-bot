### Контроль прода (после каждого деплоя и по требованию)

```bash
ops/aiqu/prod_check.sh                  # версия = origin/main, контейнер, ошибки в логах, цикл дайджеста, БД, диск, бэкап
ops/aiqu/prod_check.sh --since 10m      # после деплоя — только свежие логи
ops/aiqu/prod_check.sh --expect <sha>   # проверка конкретной ревизии
```

Только чтение, один ssh-сеанс (`PROD_SSH`, по умолчанию `aiqu`). Скрипт последовательно выводит статус каждого компонента (`OK`, `WARN`, `ALERT`), возвращая код выхода 1 при наличии хотя бы одного `ALERT`:
1. **Версия кода**: хеш HEAD на сервере против ожидаемого (`--expect`, по умолчанию `origin/main`). ALERT при расхождении.
2. **Рабочее дерево**: проверка модификаций (`git status --porcelain`). Изменения compose не считаются ошибкой, остальные вызывают WARN.
3. **Состояние контейнера**: статус `unagi-bot` (`running restarting=false`). ALERT при сбое, перезапусках или отсутствии.
4. **Логи приложения**: подсчёт строк `ERROR`, `CRITICAL` и `Traceback` за указанный интервал (`--since`, по умолчанию `45m`) и вывод последней ошибки. ALERT при наличии ошибок.
5. **Цикл дайджеста**: отметка времени последней строки `digest_cycle` в логах (WARN, если цикл не выполнялся за интервал).
6. **Сборки Ленты**: число записей `feed_build` в логах за интервал.
7. **Целостность БД**: выполнение `sqlite3 -readonly storage/bot_data.db 'pragma quick_check;'` и подсчёт таблиц. ALERT при ошибках SQLite.
8. **Дисковое пространство**: процент занятого места на корневом разделе (ALERT при `disk_pct >= 85%`, порог переопределяется `ALERT_DISK_PCT`).
9. **Диск Docker (`docker system df`)**: детализация использования диска подсистемой Docker (образы, кеш сборки, контейнеры) для оперативного контроля при 85–86% заполнении диска.
10. **Свежесть резервной копии**: возраст новейшего снимка БД (WARN при отсутствии или возрасте `> 48` часов).
11. **Память контейнера**: текущее потребление ОЗУ (`docker stats --no-stream`).
12. **Снимки БД (BK1)**: статистика каталога `storage/backups/` — число несжатых (`.db`) и сжатых (`.db.gz`) копий, общий объём каталога и размер файла БД в МБ.
13. **Цифры для решений владельца (OPS1, `ops/aiqu/prod_stats.sql`)**:
    - `failed/total за 30 дн`: число окончательно сбойных (`failed_permanent`) и общее число напоминаний за 30 суток (оценка необходимости резервной доставки в MAX);
    - `активных подписок/пользователей`: число активных подписок дайджеста и уникальных пользователей с ними;
    - `каналов с конфликтом`: число каналов, подписанных одним пользователем с несколькими тегами или периодами (для правил разрешения конфликтов Очереди 4).
14. **Конфликты слияния и docker-compose.yml**:
    - ALERT при наличии неразрешённых путей (`git ls-files -u`) или маркеров конфликта (`<<<<<<<`, `>>>>>>>`) в `docker-compose.yml` (сбой деплоя 17.10 при autostash);
    - WARN, если `docker-compose.yml` изменён вручную (напоминание выносить настройки в `.env`).
15. **Права процесса (харденинг)**: проверка `/proc/1/status` контейнера: не-root uid (в штатном контейнере — `bot:10001`), сброс Linux capabilities (`CapEff: 0000000000000000`), флаг `NoNewPrivs: 1`. WARN при работе от root (`Uid: 0`) или наличии capabilities.
16. **Email-дайджесты**: проверка доступности и чтения SMTP-конфига ботом от uid 10001 (`python -c 'import email_digest; print(email_digest.is_enabled())'`).

### Деплой и лимит CPU контейнера

Деплой выполняется автоматически через GitHub Actions (`.github/workflows/deploy.yml`) на push в `main`:
1. `git checkout HEAD -- docker-compose.yml` — сбрасывает локальные ручные правки compose на сервере.
2. `git pull --ff-only origin main` — строго fast-forward слияние (убран флаг `--autostash`, который 17.10 при конфликте возврата stash возвращал код 0, оставляя маркеры конфликта в YAML).
3. `test -z "$(git ls-files -u)"` — предохранитель: при неразрешённых конфликтах деплой немедленно останавливается с кодом 1.
4. `python3 ops/aiqu/backup_db.py --db storage/bot_data.db` — создание и валидация снимка БД. Нет снимка — нет деплоя.
5. `docker compose up -d --build` — пересборка и запуск контейнера.
6. Очистка диска от мусора сборщика: `docker image prune -f` и `docker builder prune -f --filter until=6h` (17.10 диск после деплоев достиг 86% при пороге тревоги 85%, поэтому окно очистки кеша сборщика сокращено с 48h до 6h; также при диске >= 85% удаляется `:rollback`).

**Лимит CPU**: `docker-compose.yml` задаёт лимит через `cpus: ${BOT_CPUS:-1.0}` (по умолчанию 1.0, так как на проде 1 vCPU; Docker отвергает значения `cpus > 1.0` при пересоздании контейнера). В `.env` на сервере задаётся `BOT_CPUS=1.0`.

### Контейнер unagi-bot: права процесса

Ревью безопасности п.7. Образ запускается через `ops/docker/entrypoint.sh`: от root он на доли секунды передаёт `storage/` пользователю bot (uid 10001, gid 10001) и кладёт безопасную копию `/root/.msmtprc` в tmpfs `/run/unagi/msmtprc` (права 0600; на хосте файл закрыт для root), затем навсегда сбрасывает права через `exec setpriv --reuid=10001 --regid=10001 --clear-groups --no-new-privs "$@"`.

Процесс бота:
- Не root (`uid 10001`, `gid 10001`).
- `cap_drop: ALL` (сброшены все Linux capabilities; временные `cap_add` в compose нужны только точке входа до сброса прав).
- `security_opt: [no-new-privileges:true]`.
- Корневая файловая система `read_only: true`.
- Записываемы только `storage/` (bind-mount), `/tmp` (tmpfs 64m) и `/run/unagi` (tmpfs 1m).
- `network_mode: host` оставлен сознательно: бот наследует маршрутизацию хоста (OVPN-туннель до Telegram DC после переезда). Снимать только с проверкой маршрутов.
- Файлы в `storage/` принадлежат uid 10001 (точка входа возвращает им владельца при старте). Скрипты на хосте (`backup_db.py`, `prod_check.sh`) работают от root и читают их напрямую.
- Проверка: `ops/aiqu/prod_check.sh` — строки «права процесса» и «email-дайджесты»; в CI тот же набор флагов проверяет шаг «Smoke test hardened container» (`ops/docker/smoke.py`).
- Откат: `git revert <коммит>` и push в main — деплой вернёт прежний образ (владелец файлов в `storage/` root не мешает: root читает всё).

### Контроль версии работающего контейнера и быстрый откат (DEP2)

17.10 дважды возникала ситуация: деплой падал при `up`, контейнер оставался на старом образе, а `prod_check.sh` рапортовал «версия OK», так как сверял только `git rev-parse HEAD` в репозитории на сервере, а не версию кода внутри запущенного контейнера.

**Метка версии контейнера:**
- В `docker-compose.yml` контейнер помечен меткой `labels: {org.unagi.git_sha: "${GIT_SHA:-unknown}"}`.
- В `.github/workflows/deploy.yml` перед `docker compose up` экспортируется `GIT_SHA="$(git rev-parse --short HEAD)"`.
- `ops/aiqu/prod_check.sh` читает метку через `docker inspect -f '{{ index .Config.Labels "org.unagi.git_sha" }}'` и выдаёт:
  * `ALERT "контейнер на старом коде: метка X, HEAD Y"` — если метка не совпадает с HEAD в git на сервере;
  * `WARN "контейнер: метка версии unknown/пустая (первый деплой после внедрения)"` — при значении `unknown`, пустой строке или отсутствии метки;
  * `OK "контейнер: код X (HEAD X)"` — при совпадении.

**Проверка живости и готовности при деплое (OPS3):**
- В `deploy.yml` сразу после `docker compose up -d` выполняется динамический опрос каждые 2 с (до `${DEPLOY_WAIT_SECS:-60}`):
  - `State.Status == running`
  - `RestartCount` не растёт в течение 10 с (допускается `RestartCount <= 1`, если после старта обеспечено 10 с непрерывной стабильности)
  - `org.unagi.git_sha == $GIT_SHA` (метка версии совпадает с коммитом деплоя)
  - Прикладной маркер готовности: `docker exec unagi-bot test -f /run/unagi/ready` (создаётся ботом после инициализации БД и роутеров).
- Если контейнер не вышел в состояние готовности за таймаут, деплой выводит последние 30 строк логов (`docker logs --tail 30 unagi-bot`), выполняет **автооткат** на образ `:rollback` (если тег существует) и завершается с ошибкой (`exit 1`), оставляя job красным.
- **Остановка и сброс WAL (OPS3):** в `docker-compose.yml` задан `stop_grace_period: 30s`; при остановке бот корректно отменяет фоновые циклы, закрывает сессии и выполняет `PRAGMA wal_checkpoint(TRUNCATE)`, предотвращая накопление WAL-логов.

**Откатный тег образа и как откатиться:**
- Перед сборкой нового образа (`up --build`) CI обновляет тег `rollback` **только если текущий контейнер полностью здоров** (`State.Status=running` и `RestartCount=0`):
  ```bash
  current_image="$(docker inspect -f '{{.Image}}' unagi-bot 2>/dev/null || true)"
  current_status="$(docker inspect -f '{{.State.Status}}' unagi-bot 2>/dev/null || echo missing)"
  current_restarts="$(docker inspect -f '{{.RestartCount}}' unagi-bot 2>/dev/null || echo -1)"
  if [ -n "$current_image" ] && [ "$current_status" = "running" ] && [ "$current_restarts" = "0" ]; then
    docker tag "$current_image" unagi-reminder-bot-bot:rollback 2>/dev/null || true
  fi
  ```
  Это гарантирует, что если деплой упал на liveness, следующий запуск не перезапишет рабочий образ сломанным.
- Очистка образов `docker image prune -f` удаляет **только dangling (безымянные)** слои без тегов (`<none>:<none>`). Образ с тегом `:rollback` защищён от удаления.
- **Политика защиты диска 9.8 ГБ (порог ALERT 85%):**
  - До сборки (OPS3): если использование диска составляет 85% или выше, перед `up --build` выполняется `docker builder prune -f` и `docker image prune -f`.
  - После сборки: если после деплоя и prune диск по-прежнему >= 85%, удаляется тег `:rollback` (`docker rmi unagi-reminder-bot-bot:rollback`) и повторно вызываются prune.
- **База данных и миграции при откате:**
  - Перед каждым деплоем `backup_db.py` сохраняет преддеплойный снимок `storage/backups/bot_data-<время>-predeploy.db` (запуск под `uid 10001`, чтобы служебные файлы `-wal/-shm` не создавались от root).
  - Если деплой применил миграции схемы БД, откат кода без отката БД оставит старый код на несовместимой новой схеме.
  - Перед запуском откаченного контейнера восстановите преддеплойный снимок БД:
    ```bash
    docker compose stop unagi-bot
    latest_backup="$(ls -1t storage/backups/bot_data-*-predeploy.db 2>/dev/null | head -n 1)"
    [ -n "$latest_backup" ] && cp "$latest_backup" storage/bot_data.db
    ```
- **Быстрый откат на сервере (без пересборки):**
  1. Переключить git-репозиторий на откатный коммит и экспортировать `GIT_SHA` (чтобы контейнер получил правильную метку версии):
     ```bash
     cd ~/projects/unagi-reminder-bot
     git checkout <sha>
     export GIT_SHA="$(git rev-parse --short HEAD)"
     ```
  2. Переключить тег `latest` на сохранённый образ `rollback` и поднять контейнер (при необходимости восстановив БД перед `up -d`):
     ```bash
     docker tag unagi-reminder-bot-bot:rollback unagi-reminder-bot-bot:latest
     docker compose up -d
     ```
  3. Проверить откат с флагом ожидаемого коммита (по умолчанию `prod_check.sh` ожидает `origin/main`):
     ```bash
     ops/aiqu/prod_check.sh --expect <sha>
     ```
- **Откат с пересборкой из git (если тега rollback нет или диск очистил его):**
  ```bash
  git checkout <sha>
  export GIT_SHA="$(git rev-parse --short HEAD)"
  docker compose up -d --build
  ops/aiqu/prod_check.sh --expect <sha>
  ```

### Пользователь деплоя (deploy): подготовка и миграция (OPS2)

В настоящее время CI-деплой через GitHub Actions (`.github/workflows/deploy.yml`) подключается по SSH от имени пользователя `root`. Для следования принципу наименьших привилегий подготовлен переход на выделенного непривилегированного пользователя `deploy`.

> [!NOTE]
> В `.github/workflows/deploy.yml` пользователь пока **НЕ** переключен: выполнена только подготовка серверного окружения, скрипта и инструкций.

#### 1. Подготовка пользователя на сервере (`setup_deploy_user.sh`)

Скрипт [`ops/aiqu/setup_deploy_user.sh`](setup_deploy_user.sh) выполняется владельцем сервера под `root` (или через `sudo`):

```bash
# Использование: setup_deploy_user.sh <файл_с_публичным_ключом> [каталог_проекта]
./ops/aiqu/setup_deploy_user.sh /tmp/deploy_id_ed25519.pub /home/deploy/projects/unagi-reminder-bot
```

Свойства создаваемого пользователя:
- **Пользователь `deploy`**: системная учётная запись с домашней директорией `/home/deploy` и командной оболочкой `/bin/bash`.
- **Без пароля**: интерактивный пароль заблокирован (`passwd -l deploy`), вход возможен только по SSH-ключам.
- **Группа `docker`**: пользователь добавлен в группу `docker` (`usermod -aG docker deploy`), что позволяет выполнять сборку и управление контейнерами через `docker compose` без прав `root`.
- **Без `sudo`**: скрипт гарантирует отсутствие прав `sudo` (удаляет пользователя из групп `sudo`/`wheel`/`admin` и удаляет конфигурации из `/etc/sudoers.d/`).
- **Ключи SSH (`~deploy/.ssh/authorized_keys`)**: добавляются из переданного файла публичного ключа (ключ в git не коммитится!). Скрипт идемпотентен: повторные запуски не дублируют уже существующие строки ключей. Права строго `0700` на `.ssh` и `0600` на `authorized_keys`.
- **Каталог проекта**: создаётся каталог `/home/deploy/projects/unagi-reminder-bot` (или указанный аргументом) и передаётся во владение `deploy:deploy`.

#### 2. Что сменить в секретах GitHub Actions при переключении

Когда владелец решит активировать запуск от пользователя `deploy`, в настройках репозитория GitHub (**Settings → Secrets and variables → Actions**) необходимо:
1. **`USERNAME`**: изменить со значения `root` на `deploy`.
2. **`SSH_KEY`**: приватный SSH-ключ должен соответствовать тому публичному ключу, который был передан в `setup_deploy_user.sh` и записан в `/home/deploy/.ssh/authorized_keys`.
3. Путь к проекту: в `deploy.yml` команда `cd ~/projects/unagi-reminder-bot` при входе под `deploy` автоматически перейдёт в `/home/deploy/projects/unagi-reminder-bot`.

#### 3. Шаги деплоя, требующие root, и варианты решения

В текущем `deploy.yml` (строка 104) выполняется шаг установки cron-файлов:
```bash
for f in ops/aiqu/cron.d/*; do [ -f "$f" ] && install -m 0644 -o root -g root "$f" "/etc/cron.d/$(basename "$f")" || true; done
```
Поскольку каталог `/etc/cron.d` принадлежит `root:root` с правами `0755`, непривилегированный пользователь `deploy` не имеет прав записи в него.

**Варианты решения:**
- **Вариант А (рекомендуемый — независимый root-скрипт/таймер):**
  Установка cron-файлов полностью выносится из шага SSH-деплоя. На сервере настраивается отдельный systemd-таймер (или cron от `root`), который периодически или по inotify синхронизирует файлы из каталога репозитория (`/home/deploy/projects/unagi-reminder-bot/ops/aiqu/cron.d/*`) в `/etc/cron.d/` с правами `0644 root:root`. Это полностью исключает необходимость каких-либо системных привилегий у пользователя деплоя.
- **Вариант Б (ограниченный sudoers только на install):**
  Если синхронизацию необходимо оставить в рамках шага деплоя, пользователю `deploy` выдаётся точечное право `sudo` без пароля исключительно на команду `install` файлов в `/etc/cron.d/`. Для этого на сервере создаётся файл `/etc/sudoers.d/deploy-cron`:
  ```sudoers
  deploy ALL=(root) NOPASSWD: /usr/bin/install -m 0644 -o root -g root /home/deploy/projects/unagi-reminder-bot/ops/aiqu/cron.d/* /etc/cron.d/*
  ```
  В `deploy.yml` команда соответственно заменяется на вызов `sudo install ...`.

#### 4. Как откатиться

Если после переключения на пользователя `deploy` возникнут проблемы с доступом или выполнением шагов:
1. В Secrets репозитория GitHub вернуть секрет **`USERNAME`** в значение **`root`**.
2. Убедиться, что приватный ключ `SSH_KEY` совпадает с ключом в `/root/.ssh/authorized_keys` (исходный доступ root не удаляется).
3. При необходимости синхронизировать код или состояние БД между `/home/deploy/projects/` и `/root/projects/`.
4. Перезапустить деплой — он снова будет выполнен от имени `root`.

### Резервные копии БД и восстановление

Перед каждым деплоем шаг CI выполняет:
```bash
python3 ops/aiqu/backup_db.py --db storage/bot_data.db
```
Правило «нет снимка — нет деплоя»: если снимок не создан или не прошёл `PRAGMA quick_check`, скрипт возвращает код 1 и деплой останавливается.

**Хранение и экономия места (BK1):**
- Ротация `--keep 14` (по умолчанию) считает снимки тега по обоим суффиксам (`.db` и `.db.gz`) вместе и удаляет самые старые; ручные файлы без шаблона имени не трогает.
- Сжатие `--keep-raw 2` (по умолчанию) оставляет несжатыми только 2 новейших снимка для мгновенного отката. Все более старые снимки атомарно сжимаются в gzip (`bot_data-<время>-<tag>.db.gz`). Сжатие сопровождается проверкой целостности распаковки и `PRAGMA quick_check`.
- Сбой сжатия не прерывает деплой (код выхода 0 и предупреждение в stderr), если сам новый снимок создан и проверен.
- *Новая арифметика места:* ранее 14 несжатых снимков (при весе базы ~100 МБ) занимали ~1,4 ГБ (~14% диска). Теперь хранятся 2 несжатых и 12 сжатых копий. При коэффициенте сжатия SQLite ~4x суммарный объём:
  `2 × 100 МБ + 12 × 25 МБ = 500 МБ` вместо 1400 МБ (экономия диска почти в 3 раза).
- Свежий снимок всегда остаётся несжатым (`.db`), поэтому `prod_check.sh` находит актуальный файл через `storage/backups/*.db` без изменений.

**Восстановление из снимка:**
1. **Из быстрого несжатого снимка (`.db`):**
   ```bash
   docker compose stop unagi-bot
   cp storage/backups/bot_data-<время>-predeploy.db storage/bot_data.db
   docker compose up -d
   ```
2. **Из сжатого архива (`.db.gz`):**
   ```bash
   # Распаковать с сохранением исходного gz-файла (-k):
   gunzip -k storage/backups/bot_data-<время>-predeploy.db.gz
   # Заменить файл БД при остановленном контейнере:
   docker compose stop unagi-bot
   cp storage/backups/bot_data-<время>-predeploy.db storage/bot_data.db
   docker compose up -d
   ```

### Перенос БД между серверами

Для безопасного переноса БД между серверами (в частности, при переезде на российский хостинг) используется утилита `ops/aiqu/export_db.py`. Она создаёт консистентный снимок SQLite через backup API в память (`:memory:`), потоково шифрует его публичным ключом `age` (`age -r`) без сохранения plaintext на диск и формирует манифест с контрольной суммой sha256 и метаданными схемы.

#### 1. Создание recovery-ключа (`age-keygen`)
Приватный ключ генерируется **вне серверов** (на доверенной рабочей машине владельца):
```bash
age-keygen -o recovery.key
chmod 600 recovery.key
```
Публичный ключ (`age1…`) из вывода команды или комментария файла передаётся на старый сервер для шифрования.

#### 2. Где хранить приватный ключ
- **Приватный ключ хранится вне сервера** (в менеджере паролей владельца или на защищённом офлайн-носителе).
- На исходный (старый) сервер приватный ключ **никогда не загружается**.
- На целевой (новый) сервер файл `recovery.key` копируется строго временно на момент выполнения `restore` и сразу удаляется (`rm -f recovery.key` / `shred -u recovery.key`).

#### 3. Порядок действий при миграции
1. **Остановка бота и экспорт на старом сервере:**
   ```bash
   # Остановка контейнера обязательна перед финальным экспортом:
   docker compose stop unagi-bot

   # Экспорт согласованного снимка:
   python3 ops/aiqu/export_db.py export \
       --db storage/bot_data.db \
       --recipient age1... \
       --out storage/exports/ \
       --tag migrate
   ```
   *Зачем останавливать старого бота:* гарантирует сброс WAL, отсутствие новых записей после создания снимка и исключает одновременный опрос Telegram Bot API двумя ботами (ошибка `409 Conflict`, потеря обновлений).
   Каталог `storage/exports/` и файлы `*.age` исключены из git и контекста Docker (`.gitignore`, `.dockerignore`). Также допустимо указывать путь вне репозитория (например, `--out /root/exports/`).
   В каталоге вывода создаются файлы `bot_data-<UTC-время>-migrate.db.age` (права 0600) и манифест `…db.age.json` (права 0600).
   Скрипт выводит одну строку вида `export ok path=… size=… sha256=…` без раскрытия содержимого БД.

2. **Копирование файлов на новый сервер:**
   Передайте зашифрованный архив и манифест на новый хост по доверенному каналу (scp/rsync через SSH с проверкой host key):
   ```bash
   scp storage/exports/bot_data-*-migrate.db.age* new-server:/tmp/
   ```

3. **Проверка целостности на новом сервере (verify):**
   Без расшифровки и без приватного ключа:
   ```bash
   python3 ops/aiqu/export_db.py verify --in /tmp/bot_data-*-migrate.db.age
   ```
   Сверяются сигнатура формата `age` (`age-encryption.org/v1`), версия манифеста (`format_version: 1`), размер и sha256 шифротекста по манифесту.

4. **Восстановление на новом сервере при остановленном контейнере (restore):**
   ```bash
   # Остановка контейнера (обязательно):
   docker compose stop unagi-bot

   # Безопасное восстановление:
   python3 ops/aiqu/export_db.py restore \
       --in /tmp/bot_data-*-migrate.db.age \
       --identity /path/to/recovery.key \
       --db storage/bot_data.db
   ```
   Внутренние гарантии и шаги `restore`:
   - Напоминание об остановке контейнера и проверка отсутствия активных WAL/SHM файлов (`bot_data.db-wal` и `bot_data.db-shm` — код 1 при обнаружении активных файлов).
   - Верификация формата `v1`, типа манифеста и sha256 по манифесту (код 5 при несовпадении).
   - Потоковая расшифровка в память, `deserialize`/запись во временный файл в целевом каталоге с правами 0600 и немедленный `PRAGMA quick_check`.
   - Защита от пустых/чужих баз: отклонение расшифрованных баз с 0 таблиц или без таблицы `app_meta` (код 5).
   - Глубокая проверка схемы: сравнение `user_version`, `app_schema` и состава таблиц/колонок. Если в экспорте есть новые таблицы/колонки, которых нет в целевой БД/коде — отказ (код 3); флаг `--force-schema` разрешает продолжение.
   - Обязательный предварительный снимок существующей БД через `ops/aiqu/backup_db.py:snapshot` с последующей ротацией и сжатием снимков тега `prerestore` (код 4 при сбое снимка, замена не выполняется).
   - Атомарная замена через `os.replace` с правами 0600, удаление временного файла в `finally`.
   - Флаг `--dry-run` выполняет все проверки без замены БД и без создания снимка.

5. **Удаление временного ключа и запуск контейнера:**
   ```bash
   rm -f /path/to/recovery.key /tmp/bot_data-*-migrate.db.age*
   docker compose up -d
   ```

6. **Контроль прода:**
   ```bash
   ops/aiqu/prod_check.sh
   ```

#### 4. Границы гарантии безопасности и модель угроз
- **Root исходного сервера** технически может прочитать живую БД (память процесса или файл на диске).
- **Конфиденциальность:** схема надёжно защищает экспортируемый файл от чтения пассивным наблюдателем. Без приватного recovery-ключа расшифровать данные невозможно.
- **Аутентичность и целостность (модель угроз):** манифест `.json` не подписан цифровой подписью, а публичный ключ шифрования доступен любому. Активный посредник в открытом канале технически может подменить архив и манифест своим шифротекстом. Поэтому передавать архив необходимо строго по **аутентифицированному каналу связи** (SSH/scp с валидацией ключа хоста) либо сверять контрольную сумму sha256 из вывода команды `export` с выводом `verify` внеполосно (out-of-band).

#### 5. Чего скрипт НЕ делает
Скрипт переносит **исключительно базу данных SQLite**. Отдельно по чек-листу переезда переносятся секреты и состояние вне git:
- `.env` с секретами и токенами бота/Telegraph;
- сессия MTProto (`TELEGRAM_USER_SESSION`);
- настройки почты `/root/.msmtprc`;
- конфигурация telemt и healthcheck (`/etc/tldw/*`).

## Доступ из России

Без VPN сервер с российских сетей не отвечает. Вероятная причина — на IP работает MTProto-прокси
(telemt), такие IP ТСПУ блокирует целиком; второй вариант — режется SSH на зарубежные IP.
Диагностика с российской сети без VPN:

```bash
for p in 443 8443 2258; do nc -vz -G 5 89.124.104.144 $p; done; ping -c 3 89.124.104.144
```

- всё по таймауту → блокирован IP: отдельный IPv4 под управление или jump-узел в России;
- 443/8443 открыты, 2258 нет → режут SSH: обернуть SSH в TLS (stunnel с сертификатом на
  отдельном порту) и `ProxyCommand openssl s_client …` на клиенте.
